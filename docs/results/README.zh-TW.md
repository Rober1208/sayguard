# 第一階段成果

本頁所有數字都是在 PC 原型（Windows 11、NVIDIA GeForce RTX 5060 Ti）上於 2026-10-18 與 2026-10-19
實測，除非標示為 **參考值**（Hailo 公開的數字）或 **估計值**（由參考值推算）。第一階段的一切都在這台 PC 上執行，
還沒有任何東西在 UGen300 上跑過。原始 JSON 檔就放在本頁旁邊（少數沒有檔案記錄的實機執行數字，會在出現處註明）；
`frozen/` 保留倉庫模式的第一次執行（見「凍結版與最終版」）。[`../FACTS.md`](../FACTS.md) 彙整了這些檔案中的主要數字。

我們的原則：功能只在有實測的地方展示，每一節都會說明哪些還沒量測；最後的「尚未量測」彙整所有缺口。

**本地 LLM 在哪些地方有實測。** SayGuard 交給一個小型語言模型（Qwen2.5-1.5B-Instruct，透過 Ollama API 提供：
第一階段在 PC GPU 上用 Ollama，第二階段在 UGen300 上用 hailo-ollama）兩件工作：把規則轉成結構化格式（中文或英文，
使用現場自己的區域名稱），以及規劃每日報告。規則的部分是 **LLM 提案、程式檢查、安全主管確認。** 報告規劃沒有人確認，
但 LLM 只能從程式列出的問題與我們寫好、審核過的對策中選擇。

| 工作 | LLM 負責 | 程式負責 | 實測結果（見下方章節） |
|---|---|---|---|
| 規則 → 規則 JSON：工地模式（安全帽） | 以受 schema 約束的 JSON 草擬規則 | 確定性檢查器以它在句子中找到的明講數字、距離、時間與物件覆寫草稿（可能漏掉某些說法）；安全主管確認後規則才生效 | 保留集（打字句子）：只用 LLM 40 %、只用規則擷取器 90 %、LLM + 檢查器 **95 %**（「口說規則：工地模式（安全帽）」） |
| 規則 → 平面圖規則：倉庫模式 | 同上，改用平面圖上的區域與倉庫偵測器的物件 | 同一個檢查器，區域名稱照現場的說法（「aisle seven」、「七號走道」）；安全主管確認 | 全新保留集（打字句子）：只用 LLM 24 %、只用規則擷取器 68 %、LLM + 檢查器 **88 %**（「口說規則：倉庫平面圖」） |
| 每日報告規劃 | 從程式列出、實際發生過的（攝影機、問題）組合中挑 3 個問題，並為每個問題從三個審核過的對策中選一個；沒有人確認這份規劃 | 計算所有數字、表格與摘要，並提供文字 | 行動指錯問題的比例（2 位盲評 AI 評審）：自由文字 20.0 % → 選單 **0.0 %**（「每日報告的建議行動」） |

本頁所有 LLM 準確度都是用 PC GPU 上 Ollama 的 qwen2.5:1.5b 量測。同一模型的 Hailo GenAI 版本（量化方式不同）
沒有量測，速度也沒有：在 UGen300 上（第二階段）產生一條規則 JSON 估計約 11.3 s（`benchmark.md`，估計值）。

## 口說規則：工地模式（安全帽）（`rule_parsing.json`、`scripts/eval_rules.py`）

這是工地模式（安全帽）的規則，每條規則適用於一組攝影機。測試句子是打字輸入的；語音辨識正確率沒有量測。
只有句子中明講的每個欄位都正確才算對：類型、物件、人數或距離、時段、持續時間（有講才算）、以及規則適用的攝影機集合。

檢查器就是對同一句話執行的確定性規則擷取器：它在句子中找到的明講數字、時間與物件會覆寫 LLM 的草稿。它可能漏掉
某些說法（漏掉的例子列在下方倉庫一節）。LLM 離線時，只用規則擷取器在這裡得到 90 %，在全新的倉庫集合得到 68 %。

| 解析方式 | 開發集（32 句，用來建立擷取器） | **保留集（20 句，從未用於調整）** |
|---|---|---|
| 只用 LLM（Qwen2.5-1.5B） | 25 % | **40 %** |
| 只用規則擷取器 | 100 % | 90 % |
| **LLM + 檢查器（實際採用）** | 96.9 % | **95 %** |

LLM + 檢查器在 PC GPU 上的解析時間：開發集平均 352 ms（最長 502），保留集平均 347 ms（最長 469）。在 UGen300 上
（第二階段）只有估計值、沒有實測：產生規則 JSON 約 11.3 s，Whisper 轉寫一句 5 s 的口說規則約 2.4 s（`benchmark.md`）。
實機伺服器上的兩個例子說明為什麼需要檢查器：「Alert me if more than two people are at the site gate after 10 pm」，
LLM 提出的時段是 22:00–00:00，檢查器套用明訂的慣例 22:00–06:00；「A區有人靠近挖土機三公尺內要立刻警告」，LLM 提出的物件是
「excavation pit」（開挖坑），檢查器改用「excavator」（挖土機）。現場用語（「A區」、「挖土機」）會以解碼提示
（decoder prompt）傳給 Whisper-Small；測試時若沒有提示，「A區」會被轉寫成「H」。

## 口說規則：倉庫平面圖（`rule_parsing_site.json`、`scripts/eval_rules.py --site`）

倉庫規則講的是 `configs/warehouse.yaml` 平面圖上的區域與倉庫偵測器的物件（堆高機、托板車、AMR……）。
句子（`tests/site_rule_sentences.json`，中英文，打字輸入）由從未看過解析器程式碼的 AI 撰寫代理與 AI 審稿代理
撰寫並標註。只有類型、物件、門檻、時段、持續時間（有講才算）與平面圖區域全部相符，且規則涵蓋每一支攝影機
（一支攝影機只看到區域的一部分；作業人員的位置在地面上）才算對。

| 解析方式 | 場域開發集（15 句；可用來修正解析器） | 保留集 v1 首次執行（25 句） | 保留集 v1 修正後（25 句；之後已看過） | **保留集 v2（25 句；全新，從未用於調整）** |
|---|---|---|---|---|
| 只用 LLM（Qwen2.5-1.5B） | 20 % | 16 % | 16 % | **24 %** |
| 只用規則擷取器 | 100 % | 80 % | 96 % | 68 % |
| **LLM + 檢查器（實際採用）** | 100 % | 84 % | 100 % | **88 %** |

LLM + 檢查器的解析時間，平均（最長）：開發集 363 ms（457）、保留集 v1 392 ms（515）、保留集 v2 395 ms（638）。
v1 的首次執行結果保留在 `rule_parsing_site_v1_first_run.json`。

各集合的用法：v1 第一次、盲測的執行得到 84 %；之後針對它漏掉的說法修正了解析器，並再量了一次 v1（100 %），
所以 v1 已不再乾淨。v2 是之後由另一組同樣沒看過解析器的 AI 撰寫與審稿代理寫成，並用修正後的解析器只量一次——
**88 % 才是誠實的數字**。解析器的修正包含：含數字或文字的區域名稱（「aisle 7」、「aisle seven」、「七號走道」）、可省略的結尾「區」（「碼頭」=「碼頭區」）、
距離的說法、停留類動詞（「stays」、「逗留」）、「N 人以上」（N or more）、緊接中文的「AMR」，以及講到區域的規則
會涵蓋每一支攝影機。

在全新的 v2 上，只用規則擷取器時，好幾種換句話說的說法完全產不出規則（「goes above 12」、
「total occupancy … exceeds 40」、「碼頭區的人數只要大於十」），而經過檢查的 LLM 草稿都答對了：這就是 LLM
留在流程中的理由。LLM + 檢查器在 v2 仍錯了三句：用「待了半分鐘」表達的持續時間、七號走道「six or more people」
（門檻）、以及「晚上八點以後，倉庫裡只要看到人就通報我」（規則類型與門檻）。每條解析出的規則都會先給安全主管
確認才生效。

## 警報的是非判斷複核：是做判斷，不是聊天（`yesno_check.json`、`probe_train.json`）

「這個人有沒有戴安全帽？」只有兩種答案，所以我們在 **同一組 193 張保留裁切圖**（94 張有戴、99 張未戴）上，
比較非生成式分類器與生成式 VLM；裁切方式與警報裁切完全相同。這些是資料集中已標註的裁切圖：94 張有戴安全帽的
裁切圖只是偵測器真實「沒戴安全帽」誤報的替代品，所以「濾除誤報」不是實測的誤報濾除率。
程式：`scripts/eval_yesno.py`、`scripts/train_probe.py`、`scripts/eval_vlm.py`。

| 方法 | 正確率 | 濾除誤報 | 保留真違規 | PC 時間，單張 | PC 時間，批次 | 檔案 |
|---|---|---|---|---|---|---|
| CLIP ViT-B/32 zero-shot（兩個文字提示） | 88.6 % | 86.2 % | 90.9 % | – | 3.49 ms | `yesno_check.json` |
| **CLIP ViT-B/32 凍結 + 線性頭（實際採用）** | **95.3 %** | 95.7 % | 94.9 % | **15.2 ms**（p95 24.7） | 3.49 ms | `probe_train.json`（批次時間：`yesno_check.json`） |
| ResNet18 微調裁切分類器 | 95.3 % | 97.9 % | 92.9 % | – | 1.7 ms | `yesno_check.json` |
| Qwen2-VL-2B，正式提示詞（生成式） | 91.7 % | 89.4 % | 93.9 % | 283 ms（p95 531） | – | `vlm_check.json` |

「單張」就是警報進行是非判斷複核的方式：暖機後每張裁切圖呼叫一次（線性頭用 `scripts/train_probe.py`，VLM 用
`scripts/eval_vlm.py`）。「批次」是把 128 張的批次時間除以張數，不能和單張時間比較。`yesno_check.json`
寫成的時間早於另外兩支程式的最終執行：實際採用那一列取自 `probe_train.json`（`yesno_check.json`
裡較早的線性頭那一列為 96.8 % / 93.9 %），VLM 那一列取自 `vlm_check.json`。

實際採用的分類頭（`scripts/train_probe.py`，2,950 張訓練裁切圖，weight decay 在 578 張驗證裁切圖上選定，
驗證正確率 0.95）是疊在 CLIP 影像特徵上的一個 2×512 矩陣。我們選它而不選 ResNet18（正確率相同），是因為它保留
較多真違規、沿用開放詞彙偵測器本來就會載入的 CLIP 權重，而且新的是非題只需要新的分類頭，不需要新的網路。
它也比 VLM 小得多、快得多。

因為是非判斷複核保留 94.9 % 的真違規而不是全部（約 5 % 被濾除，1 − 0.949，`probe_train.json`），被濾除的警報
會留在清單中（變暗顯示），而不是刪除。VLM 仍可選用（`verifier.backend: vlm`）。

## 每日報告的建議行動（`report_actions.json`、`scripts/eval_report.py`）

每日報告的每個數字、表格與摘要都由程式從警報紀錄計算（預設 `mode="hybrid"`）；本地 LLM 只負責規劃三項
建議行動，而且沒有人確認這份規劃（它只能選擇列出的問題與審核過的對策）。測試時，由 Qwen2.5-1.5B 撰寫
整份報告雖能通過「數字都出自統計」的檢查，仍會把次數算到錯的對象並自創用語，所以全 LLM 模式需要手動開啟
（`build_report(..., mode="llm")`）。

建議行動的產生方式（`sayguard/report.py`）：

- **menu（選單，預設，`actions="menu"`）**：程式列出實際發生過的（攝影機、問題）組合，依次數由多到少排列，
  再加上有誤報被濾除的攝影機。LLM 挑出 3 個不同的問題，並為每個問題從該類問題的三個審核過的對策中選一個。
  它的回覆受 JSON schema 約束，欄位都是列舉值（清單中的問題編號、對策 0–2），所以它不寫任何文字，也不可能
  講出沒發生的攝影機或問題。
- **structured（結構化，`actions="free"`）**：LLM 依編號挑 3 個問題，並為每個問題寫一句行動；攝影機與問題由
  程式填入，若行動提到別支攝影機、統計裡沒有的數字或另一類問題，就改用範本文字。
- **free text（自由文字，舊提示詞，保留作為基準）**：根據少數幾個事實寫 3 行 markdown 條列，只檢查有沒有自創數字。

測試：20 個合成的日子（英文與中文交替），三種方式用同樣的日子，模型為 Qwen2.5-1.5B（PC GPU 上 Ollama 的
qwen2.5:1.5b）。

**關鍵字檢查**（自動）：行動文字中出現某支攝影機設定的名稱（不分大小寫），就算「有提到攝影機」；若提到某支攝影機，
卻搭配那支攝影機當天沒有發生的問題類型，就算歸錯對象。

| 方式 | 被接受的日子 | 行動數 | 有提到攝影機 | 歸錯對象 |
|---|---|---|---|---|
| 自由文字（舊提示詞） | 20/20（100 %） | 60 | 45 | 8（13.3 %） |
| 結構化（`actions="free"`） | 19/20（95 %） | 57 | 57 | 0（0.0 %） |
| **選單（預設）** | 20/20（100 %） | 60 | 60 | **0（0.0 %）** |

**獨立盲評審**：每項行動由 2 位 AI 評審（獨立的評審代理，不是人）評分，評審不知道是哪種方式寫的，但拿得到
每支攝影機當天真正發生的問題。兩位評審對「指錯問題」的判斷在 177 項中有 176 項一致。

| 方式 | 行動數 | 指錯問題（兩位都認為） | 指錯問題（任一位認為） | 合理（兩位都認為） | 有提到攝影機 |
|---|---|---|---|---|---|
| 自由文字 | 60 | 20.0 % | 20.0 % | 45.0 % | 88.3 % |
| 結構化 | 57 | 3.5 % | 5.3 % | 52.6 % | 100.0 % |
| · LLM 自己寫的文字 | 43 | 4.7 % | 7.0 % | 37.2 % | 100.0 % |
| · 被換成範本文字 | 14 | 0.0 % | 0.0 % | 100.0 % | 100.0 % |
| **選單（預設）** | 60 | **0.0 %** | **0.0 %** | **100.0 %** | 100.0 % |

自由文字的兩個「有提到攝影機」數字量的是不同的東西：關鍵字檢查只計算文字中出現攝影機設定名稱的行動（不分大小寫；60 項中 45 項），
評審則連用其他說法指稱某支攝影機的也算進去（60 項中 53 項，88.3 %；兩位評審對全部 60 項的判斷一致）。多出來的 8 項
全是把攝影機名稱翻成中文的中文行動，例如以「焊接區」指 Welding Bay（`report_actions_judging/`）。對選單行動而言，
「合理」評的是問題與對策的選擇，因為文字是我們寫好、審核過的，所以它的 100.0 % 不能和 LLM 自己寫文字的那幾列直接比較。

關鍵字檢查太寬鬆：它在結構化模式找不到任何歸錯，評審卻找出 3.5–5.3 %。當 1.5B 模型自己寫文字時，兩位評審都
認為合理的只有 37.2 %；改成從審核過的對策中選擇後，這些日子裡指錯問題的行動完全消失。所以 LLM 的工作是程式
做不到的部分——判斷哪些問題重要、哪個對策適合——而它輸出的任何東西都不可能是錯的攝影機或錯的數字。

限制：資料是合成的日子，不是真實工地的紀錄。評審是 AI 代理，不是安全主管；評審提示詞、盲評批次、答案表與每一則
判斷都在 [report_actions_judging/](report_actions_judging/README.md)，被評審的那一次執行保存為
`report_actions_judged.json`。`scripts/eval_report.py` 只能重現關鍵字檢查；重新執行會改寫 `report_actions.json`，
且不含 `independent_judges` 區塊。

## 倉庫模式（`site_eval*.json`）

倉庫模式把一座倉庫中已校正的攝影機融合到它的平面圖上：每位作業人員只算一次，而不是每支攝影機各算一次；區域與距離
以地面上的公尺計；一條規則對每位作業人員每次進入只發一次警報，而不是每支攝影機各發一次（運作方式見
[`../SITE_MODE.zh-TW.md`](../SITE_MODE.zh-TW.md)）。
`scripts/eval_site.py` 在同步的串流上逐格執行與實機完全相同的融合流程（`SiteFusion` + `RuleEngine.evaluate_site`），
並與 NVIDIA 的真值（ground truth；PhysicalAI-SmartSpaces，合成資料，CC BY 4.0）比對；真值知道每個人在地面上的
位置，以及他在每支攝影機中的身分。真值從不進入流程。每個場景：3,000 張影格、10.0 fps（W022：3,090 張）。

### 量測項目

- **人數**：逐格平均的真實人數（至少被一支設定中的攝影機看到的人）、倉庫模式的作業人員數、以及各攝影機人員追蹤數
  的總和（逐支攝影機系統會數出的人數）；以及各自的平均絕對誤差。
- **位置**：作業人員與真實人員在地面上 1 m 內配對：召回率、精確率、MOTA、平均位置誤差、重複（同一時間一個人身上
  有兩個作業人員 ID 的人‧影格比例）、IDF1，以及每個真實人員被拆成幾個 ID。
- **堆高機**：堆高機影格（有堆高機出現在設定中的攝影機裡）中，偵測到的堆高機其著地點碰到真實堆高機底面
  （容許 2.5 m）的比例；量到的作業人員與堆高機距離減去與堆高機 3D 底面的真實距離（絕對誤差中位數、MAE、
  帶正負號的平均誤差 = 偏差）。
- **警報**：真值事件是一個人在堆高機 3 m 內持續 2 s（規則「Keep 3 m from forklifts」，冷卻時間 60 s），或在某個
  地面區域內持續 3 s（`--all-zones` 為每個區域加上一條 3 s、冷卻 60 s 的在場規則；W010 的七號走道規則是設定檔
  原有的，同樣是 3 s、60 s）；短於 1 s 的中斷不會把事件切開。若警報對應的作業人員在發報時位於同一規則某事件的人
  2.5 m 內，該警報就屬於那個事件；不屬於任何事件的警報即為 **誤報**。
  - **涵蓋** = 有自己警報的事件 + 在同一人上一次警報的冷卻時間內開始的事件（依設計不再發新警報：冷卻時間用來
    拉開提醒間隔）；
  - **嚴格召回率** = 有自己警報的事件；
  - **每個有警報事件的警報數** = 事件上的警報數 ÷ 有警報的事件數（1.0 = 沒有重複）。
- **逐支攝影機模式**（基準）：同樣的偵測結果、同樣的地面距離，但每支攝影機的追蹤各自發報，並沿用 SayGuard 先前
  的逐支攝影機防重複機制（同位置 IoU、每支攝影機 15 s、每支攝影機一個在場對象）。它與倉庫模式唯一的差別，
  是跨攝影機時每位作業人員只有一個身分。

### 凍結版與最終版

`frozen/` 存放凍結參數的那次執行；最上層的 `site_eval*.json` 是最終版。兩者之間改了警報邏輯；偵測器與
信心值設定都維持不變：

1. **同一位作業人員還是另一個人。** 在冷卻時間內被警報過的作業人員附近出現新的作業人員 ID 時，只有兩種情況視為同一人：
   那位作業人員仍被追蹤，而新 ID 就站在他身上（同一個人身上的第二個 ID）；或那位作業人員自己的 ID 已經消失，而新 ID
   在被警報的位置附近 10 s 內出現（`SITE_REAPPEAR_S`），或在最後被看到的位置附近 3 s 內出現、半徑以步行速度
   擴大（`SITE_HANDOVER_S`）。其他人——例如沿同一條走道走來的下一位作業人員——會有自己的警報。
2. **重新進入。** 對在場規則而言，離開區域 10 s 以上（`SITE_REENTRY_S`）後再回來，算是新的進入，不論是否在
   冷卻中都會再發警報；冷卻時間只用來拉開某人持續停留時的提醒間隔。

兩項修正都只在 W009、W012、W017 與 W020 上開發與檢查，時間在看過測試場景的凍結版結果之後
（`site_preregistration.md`）；W017 與測試場景 W018 是同一棟建築、同一組攝影機。之後測試場景只重跑了一次。

涵蓋的事件，凍結版 → 最終版：門口／碼頭 94 % → 100 %、堆高機 3 m 89 % → 92 %、走道／通道 64 % → 83 %、
作業區 83 % → 96 %、其他區域 71 % → 90 %。警報與誤報也隨修正增加：門口／碼頭警報 26 → 52 次（都不是誤報）、
走道 40 次中 1 次 → 77 次中 3 次誤報、作業區 244 次中 16 次 → 362 次中 26 次、其他區域 30 次中 4 次 → 44 次中 6 次
（見上表）。凍結版是在修正之前量的，所以是較乾淨的保留集結果；最終版描述目前的程式。重新進入就發報
也代表繁忙的作業區會有重複警報（W010 open_floor：48 個事件發了 130 次警報，每個有警報事件 2.93 次）。

### 限制

- **只有合成影片。** 尚未量測任何真實倉庫；真實攝影機也需要各自校正。
- **測試場景並非完全獨立。** W010 是展示場景：追蹤器是一邊看著它一邊開發的，區域也來自展示設定檔。用來開發警報
  邏輯的 W017 與測試場景 W018 是同一棟建築、同一組攝影機，而且兩項警報邏輯修正是在看過測試場景的凍結版結果之後
  才做的。
- **測試後沒有重新訓練。** 不犧牲一個測試場景就無法重新訓練偵測器，所以漏偵測都留在這些數字裡：W018 與 W019 上
  只在 0.169 與 0.115 的堆高機影格中找到堆高機（W022 為 0.793、W010 為 0.986）；原因尚未確定。
- **身分維持時間短**（測試場景 IDF1 0.287–0.977，每人最多 10.72 個 ID；ID 在幾十秒內就會更換）：警報是以冷卻
  時間內的作業人員為單位，不是以長期身分為單位，而且從不顯示作業人員 ID。
- **距離**：W022 的堆高機距離偏差為 0.43 m，量得比實際遠，這是不安全的方向。對其他車輛類別的距離沒有實測。
- **繁忙區域的重複警報與誤報**：W010 racks 56 次警報中 13 次誤報；W010 open_floor 每個有警報事件 2.93 次。
- **部分規則的嚴格召回率偏低**（測試場景的堆高機規則 41 %、W019 堆高機 0.273、W015 south_staging_floor 0.467）：
  依設計，冷卻時間會壓下同一人的第二次警報；「涵蓋」會計入這些事件，嚴格召回率不會。
- **超出規格**：W020（16 支攝影機，但人也最多，又是訓練建築）的 MOTA 只有 0.168；原因尚未確定。
- 每個場景只執行一次；沒有信賴區間。


`eval_site.py` 會寫入工作目錄的 `results/` 與 `docs/results/`。`--dets-cache FILE` 會在第一次執行時存下偵測器輸出，
之後重播（不需 GPU 就能量測追蹤器與規則的修改）；`--tag NAME` 把實驗結果只寫到工作目錄。`frozen/` 是凍結參數那次
執行的複本；先前的警報邏輯沒有保留，所以無法從目前的程式重跑。`eval_rules.py --site --dev` 只跑開發集、
只寫到工作目錄；完整的 `--site` 執行會再量一次保留集 v2，那就不再是第一次量測。

## Hailo-10H：安全帽偵測器已編譯，兩個網路都在 Hailo 模擬器中逐位元驗證（`hailo/`）

在沒有裝置的情況下，第一階段已讓工地模式（安全帽）的兩個視覺網路走完真正的 Hailo 工具鏈（Dataflow Compiler
5.4.0 + Hailo Model Zoo 配方，在 WSL 中），並用 DFC 模擬器量測 INT8 的代價；模擬器的 `SDK_QUANTIZED` 情境會重現
晶片的整數運算。只有安全帽偵測器編譯成了 HEF，而且從未在硬體上執行；是非判斷複核的 CLIP 影像編碼器只做了量化
並在模擬器中檢查，沒有 HEF。DFC 的 TensorFlow 不支援 RTX 50 系列 GPU，所以全部在 CPU 上執行，沒有使用只限 GPU
的微調等級：偵測器使用最佳化等級 1（equalization + bias correction）、512 張校正影像與 activation clipping；CLIP 編碼器使用
Model Zoo 自己的腳本（等級 0、16 位元的 layer norm 與 residual add）。

**安全帽偵測器**（`hailo_int8.json`、`pc_baseline.json`；`hailo/build_helmet.py`、`hailo/eval_int8.py`、
`hailo/eval_pc_baseline.py`）。同樣 2,001 張測試影像、同樣的 COCO 評估器（pycocotools）、與 HEF 相同的 NMS 設定
（分數 ≥ 0.2、IoU 0.7）：

| 模型 | mAP50 | mAP50-95 | 安全帽 AP50 | 未戴安全帽 AP50 |
|---|---|---|---|---|
| PC，PyTorch fp32（`pc_baseline.json`） | 0.8927 | 0.5663 | 0.9035 | 0.8819 |
| Hailo 圖，浮點（`SDK_FP_OPTIMIZED`） | 0.8927 | 0.5662 | 0.9035 | 0.8819 |
| **Hailo INT8（`SDK_QUANTIZED`，晶片實際的運算）** | **0.889** | 0.56 | 0.9008 | 0.8772 |

浮點的 Hailo 圖與 PyTorch 相差在 0.0001 以內，代表解析與模型腳本都正確；INT8 的代價是 mAP50 少 0.0037、
mAP50-95 少 0.0062。

校正集的影響很大（見下表）。校正影像來自驗證集，從不用測試集；但下列三種版本都在同一個測試集上評估，實際採用的
版本是根據這些測試結果選出來的：64 張的版本 mAP50（0.8911）與未戴安全帽 AP50（0.8841）較高，實際採用的版本
mAP50-95（0.56）較高。因此公布的 INT8 數字是在測試集上挑選的結果，不是單一次的盲測。

| 校正 | mAP50 | mAP50-95 | 未戴安全帽 AP50 | 檔案 |
|---|---|---|---|---|
| 64 張，隨機抽樣（seed 0） | 0.8911 | 0.5396 | 0.8841 | `helmet_c64_optimized_int8.json` |
| 512 張 | 0.8513 | 0.5363 | 0.857 | `hailo_int8_c512.json` |
| **512 張 + activation clipping（0.01–99.99 百分位），實際採用** | 0.889 | **0.56** | 0.8772 | `hailo_int8.json` |

我們的解讀（沒有另外量測）：影像越多，少數離群值會撐大 activation 範圍，使 INT8 的量化步距變粗；把範圍截在
0.01–99.99 百分位後，框的位置（mAP50-95）最接近浮點。（上方偵測器表中的 0.9393 是 Ultralytics 自己在分數 ≥ 0.001 下的指標；
同門檻下 pycocotools 為 0.9245（`pc_baseline.json`）。這裡兩欄較低，是因為 HEF 內建的 NMS 有 0.2 的分數下限。
0.889 只能和 0.8927 比，不能和 0.9393 比：兩者是不同的評估方式。）

HEF（`helmet_yolov8s.hef`）以 `compiler_optimization_level=max` 編譯，與 `hailomz compile --performance` 相同；
它還沒有在硬體上執行過。上面的 0.889 是在模擬器中量測量化後的模型，不是執行 HEF 得到的。沒有裝置時，profiler 無法給出多 context 網路的 FPS；同一個 YOLOv8s 在 Hailo-10H 上的參考值是 batch 1 時 166 FPS、
batch 8 時 252 FPS（Hailo Model Zoo，**參考值**）。

**是非判斷複核用的 CLIP 影像編碼器**（`clip_probe_int8.json`；`hailo/clip_probe_int8.py`）。Model Zoo 的
`clip_vit_b_32_image_encoder` 搭配其模型腳本，以訓練集中 64 張現場裁切圖校正，測試用同樣的 193 張裁切圖；
只做了量化並在模擬器中執行（沒有 HEF）：

| 特徵 → 分類頭 | 正確率 | 濾除誤報 | 保留真違規 |
|---|---|---|---|
| PC PyTorch（GPU 上 fp16）→ 用 PC 特徵訓練的分類頭（目前採用） | 95.3 % | 95.7 % | 94.9 % |
| Hailo INT8 → 同一個 PC 分類頭 | 94.3 % | 95.7 % | 92.9 % |
| **Hailo INT8 → 用 INT8 特徵重新訓練的分類頭** | **95.3 %** | 96.8 % | 93.9 % |

浮點的 Hailo 特徵與 PyTorch 編碼器一致（與其 GPU fp16 特徵的 cosine 為 0.9999）；INT8 特徵的 cosine 為 0.9634。
沿用 PC 分類頭，正確率會掉一個百分點（94.3 %），保留的真違規也較少（92.9 %）。用晶片自己的特徵重新訓練 2×512
分類頭可以補回正確率（95.3 %），但保留真違規為 93.9 %，PC 上則是 94.9 %；所以第二階段會用裝置特徵重新訓練分類頭。

**倉庫模式**：倉庫偵測器（`site_yolov8s`，6 類，960 px）還沒編譯成 HEF（`configs/warehouse.yaml` 的 `detector.hef`
標示為「not built yet」）；它的 INT8 準確度沒有量測。
