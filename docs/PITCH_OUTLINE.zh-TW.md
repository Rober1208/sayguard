## 貫穿整份簡報的主線：本地 LLM 拿來做什麼

評審會看到很多偵測器。SayGuard 不一樣的地方，在於它怎麼使用一個小型的本地 LLM（Qwen2.5-1.5B-Instruct，
透過 Ollama API 呼叫）。Stage I 它在 PC GPU 上由 Ollama 執行；Stage II 會搬到 UGen300，由 hailo-ollama
提供同樣的 API。LLM 負責兩件偵測器做不到的事。原則就是第 5 頁的標題：**LLM 提案、程式檢查、安全主管確認。**
對規則來說，這句話字字成立。每日報告的規劃沒有人確認，所以在那裡 LLM 只能「選」：問題只能從實際發生過的
問題裡選，措施只能從審核過的清單裡選。

1. **把一句話變成規則，用現場自己的說法。** 模型依照從 SayGuard 規則模型產生的 JSON schema 填寫欄位。
   接著確定性的檢查器會覆寫它在句子裡找到的數字、距離、時間、持續時間和物件。它可能漏掉某種說法，這也是
   規則生效前要讓安全主管先看白話版規則內容的原因之一。在打字輸入的保留測試句上（規則完全正確的比例；不含
   語音辨識），工地模式（安全帽）從「只用 LLM」的 40 % 提升到「加上檢查器」的 95 %；倉庫模式在第一組盲測句上
   （第一次量測）從 16 % 提升到 84 %，在全新一組上從 24 % 提升到 88 %。語言也屬於這件工作。規則可以用中文或
   英文說。Whisper 會先拿到現場的區域與攝影機名稱作為提示，LLM 也會拿到中英文兩種區域名稱。不管區域名稱裡的數字寫成
   阿拉伯數字、中文數字或英文單字（七號走道、7號走道、aisle seven），後面有沒有「區」，檢查器都認得。簡體中文
   輸出會轉成台灣繁體用語。語言只在規則測試裡一併量測：每一組規則測試句都混合了中文和英文句子。在 PC 上解析
   一條規則平均 0.35–0.40 秒（保留集最長 0.64 秒）。LLM 離線時，規則擷取器（確定性的部分，檢查器用的也是它）
   會單獨解析規則：工地模式保留集 90 %，全新的倉庫保留集 68 %。在那組句子上，有好幾種換句話說的寫法它完全產生
   不出規則，而經過檢查的 LLM 草稿答對了，這就是 LLM 要留在流程裡的原因。
2. **規劃每日報告。** 每個數字、表格和摘要都由程式計算。模型只看到實際發生過的（攝影機、問題）組合，
   以及每組各三項審核過的改善措施，並以 JSON schema 回傳問題編號和措施編號，所以它不可能點名一支沒出問題的
   攝影機，也不可能編造數字。每項措施由兩位 AI 盲評：讓模型自由撰寫的措施有 20.0 % 指錯問題；由模型挑問題、
   自己寫措施（有關鍵字檢查）時是 3.5 %；目前採用的設計是 0.0 %。

所有 LLM 的準確率都是在 PC GPU 上用 Ollama qwen2.5:1.5b 量測的。同一個模型的 Hailo GenAI 版本使用不同的量化
方式，還沒有量測。LLM 只在需要時才執行（新增一條規則或產生一份報告），所以不會每張影格都和偵測器搶運算資源。
Hailo GenAI Model Zoo 列出的 Qwen2.5-1.5B-Instruct 在 Hailo-10H 上是 7.35 tokens/s，第一個 token 0.37 秒。
依這些數字，`docs/results/benchmark.md` 估計在 UGen300 上從語音規則到規則 JSON 約 11.3 秒，Whisper 轉錄一段
5 秒的規則約 2.4 秒（估計值，未實測）。在簡報裡，這條主線是第 5–8 頁；Demo 影片會展示這兩件事。

## 逐頁說明

### 1 · cover：SayGuard

*投影片上：* 上方標籤「ASUS UGEN AI LEAGUE · STAGE I PROPOSAL」；「One UGen300 per site area. Every camera
watched. Rules you can say.」（每個場區一台 UGen300，每支攝影機都看住，規則用說的）；標籤「Battlefield Lightning ·
UGen300」、「Workplace AI」、「[Team name] · [Onsite / Global Online track]」。

SayGuard 是整個場區每支攝影機的安全助手，而且用講話就能設定。它有兩種模式：工地模式（安全帽）檢查每支攝影機
畫面裡有沒有人沒戴安全帽；倉庫模式把所有攝影機合成一張平面圖。我們展示的每個結果，都是在可運作的 Stage I
原型上量測的，這個原型跑在 PC GPU 上。Stage II 會搬到每個場區一台 ASUS UGen300。在 Stage II 實機量測之前，
UGen300 的數字都是依 Hailo 公開資料推算的估計值。

### 2 · problem：Sites have cameras. Few have anyone watching them live.（現場有攝影機，但很少有人即時在看）

*投影片上：* 三張卡片：「Found too late」（發現得太晚：沒戴安全帽可能要等出事後回放錄影才被發現）；「Rules are
fixed」（規則是固定的：許多 AI 攝影機出廠就是一份固定的規則清單，新增區域、距離、人數或時段規則就得手動重新設定）；
「Alarms get ignored」（警報被忽略：誤報頻繁會磨掉信任，而把現場影片串流到雲端會引發隱私與頻寬疑慮）。

這裡講三個問題。第一，很少有現場有人即時看著攝影機，所以沒戴安全帽可能要等出事後回放錄影才被發現。第二，許多
AI 攝影機出廠就是一份固定的規則清單，而且要一支一支設定，新增一個區域、距離、人數或時段規則就得手動重新設定。
第三，常常出錯的警報會磨掉信任、被大家忽略，而改把現場影片串流到雲端，又會引發隱私與頻寬疑慮。

### 3 · idea：One box next to the recorder. Every camera covered.（錄影主機旁一台設備，涵蓋每支攝影機）

*投影片上：* 流程：現場原有的攝影機（RTSP；只有在監看區域被少於兩支攝影機看到的地方才加攝影機；不上雲）→
主機 + ASUS UGen300（批次偵測器、CLIP 是非判斷複核、Whisper 和 Qwen2.5，全部在現場：目前在 PC GPU 上，
Stage II 在 UGen300 上）→ 安全主管（經複核的警報、即時平面圖、每日報告、用語音新增規則）。兩張模式卡片：
「Hard-hat mode: construction sites, hard hats on every camera」（工地模式（安全帽）：每支攝影機檢查安全帽）與
「Warehouse mode: all cameras fused on one floor plan, zones and forklift distances in metres」（倉庫模式：所有
攝影機合成一張平面圖，區域與堆高機距離以公尺計）。

一張圖講完整個產品。現場保留原本的攝影機，只在監看區域被少於兩支攝影機看到的地方補一支。我們在錄影主機旁
加一台小主機和一台 UGen300。所有模型都在現場執行：Stage I 原型是在 PC GPU 上，Stage II 則在 UGen300 上。
安全主管得到經複核的警報、即時平面圖、每日報告，還能用語音新增規則。兩種模式共用同一套流程，差別只在看什麼：
工地模式（安全帽）是逐支攝影機檢查安全帽，倉庫模式則是在同一張平面圖上看人員和車輛。

*投影片上：* 工地模式（安全帽）儀表板截圖；說明文字「10 looping demo streams, analysed live · alerts

這是真正的儀表板，1920 × 1080（截圖的尺寸），十路循環播放的 demo 串流，每路以每秒十張影格為目標分析。紅框是

### 5 · llm：A small LLM proposes. Code checks. The officer confirms each rule.（小 LLM 提案，程式檢查，每條規則由安全主管確認）

*投影片上：* 上方標籤「INNOVATION · THE LOCAL LLM · TWO JOBS」（創新 · 本地 LLM · 兩項工作）。工作 1「Turns a
sentence into a rule」（把一句話變成規則）：工地模式（安全帽）40 % → 95 %，倉庫模式 16–24 % → 84–88 %（打字輸入的
保留測試句，只用 LLM → 加上檢查器；只用檢查器的規則擷取器是 90 % / 68–80 %）。工作 2「Plans the daily report」
（規劃每日報告）：指錯問題 20 % → 0 %（自由撰寫 → 審核過的措施，兩位 AI 盲評）。第三張卡片「Speaks like the site」
（說現場的話）講的是兩項工作共通的語言能力，不是第三項工作：中文或英文、台灣用語、區域名稱照大家的叫法（「七號走道」、
「aisle seven」）；離線時規則擷取器單獨仍能解析 68–90 % 的打字保留測試句。下方橫條：「…after 10 pm」→ LLM
22:00–00:00 → 檢查器 22:00–06:00。頁尾：量測使用 PC GPU 上經 Ollama 執行的 Qwen2.5-1.5B-Instruct；UGen300 版本
（hailo-ollama）尚未量測。

這是我們最主要的創新。15 億參數的模型不夠可靠，不能單獨信任，所以我們從不單獨信任它。Hailo 有公開它的
Hailo-10H 版本（7.35 tokens/s）；和偵測器一起跑的情況會在 Stage II 量測。這個模型有兩個工作。第一，把一句話
變成規則，中文或英文都可以，並使用現場自己的區域名稱：它在句子裡找到的數字、時間和物件都由確定性程式覆寫，最後
由安全主管確認。在打字輸入的保留測試句上，這讓工地模式（安全帽）的正確率從 40 % 提升到 95 %，倉庫模式從 16–24 %
提升到 84–88 %。規則擷取器單獨就能處理常見的說法（90 % / 68–80 %），模型補上它漏掉的換句話說。第二，規劃
每日報告：每個數字都由程式計算，模型只挑出最重要的三個問題，並替每個問題選一項審核過的措施。這份規劃沒有人確認，所以模型只被允許從這些清單裡選。兩位 AI 盲評發現它的措施沒有一項指錯問題，自由撰寫時則有
20 %。下方的例子是真的：「after 10 pm」模型給的是 22:00 到 00:00，檢查器套用明訂的慣例，改成 22:00 到 06:00。
這些準確率是在 PC 上用 Ollama 量測的；Hailo 版本會在 Stage II 量測。

### 6 · voice：Speak a rule, confirm it, it is live（說出規則、確認、立即生效）

*投影片上：* 四個步驟：說（Whisper-Small，以現場詞彙作為解碼提示）→ 草擬（Qwen2.5-1.5B，依固定 schema 輸出
JSON）→ 檢查（確定性檢查器：覆寫它在句子裡找到的數字、時間和物件）→ 確認（安全主管看過白話版規則後把它切換為
生效）；一行說明「LLM offline? The checker's rule extractor alone still parses 68–90 % of typed held-out sentences」
（LLM 離線時，檢查器的規則擷取器單獨仍能解析 68–90 % 的打字保留測試句）；以及「Say a rule」面板截圖。

流程有四個步驟。Whisper-Small 轉錄中文或英文，並先拿到現場的區域與攝影機名稱作為提示；它對錄音語音的辨識
準確率還沒有量測。Qwen2.5-1.5B 依照從規則模型產生的 JSON schema 填寫，所以它會用規則本身的欄位回答。檢查器
擷取它在句子裡找到的明確內容，兩邊不一致時一律以它為準；每次覆寫 LLM 的結果都會寫下備註，讓安全主管看得到
修正了什麼，檢查器漏掉的說法則在安全主管確認時攔下。不涵蓋任何攝影機的規則無法啟用。LLM 離線時，規則擷取器
會單獨解析規則（工地模式保留集 90 %，全新倉庫保留集 68 %）。在 PC 上每條規則平均解析 0.35–0.40 秒（最長 0.64 秒）。
在 UGen300 上估計每條規則約 11.3 秒，另加轉錄一段 5 秒規則約 2.4 秒（依 Hailo 公開數據推算的估計值，未實測）。

### 7 · accuracy：With the checker, a 1.5B model gets 84–95 % of held-out rules exactly right（加上檢查器，1.5B 模型在 84–95 % 的保留測試規則上完全正確）

*投影片上：* 兩組長條（只用 LLM / 只用規則擷取器 / LLM + 檢查器）。工地模式（安全帽），20 句打字輸入的保留
測試句：40 %、90 %、95 %。倉庫模式，2 × 25 句打字輸入的保留測試句：16–24 %、68–80 %、84–88 %。一行說明：84 %
是第一組在修正它暴露的問題之前的第一次量測；88 % 是修正後全新的第二組。頁尾：PC GPU 上的 Ollama qwen2.5:1.5b、
`scripts/eval_rules.py [--site]`、`docs/results/rule_parsing*.json`。

一條規則要每個標註欄位都對才算正確：規則類型、物件、人數或距離、時段、有說到的持續時間，以及涵蓋的攝影機
或區域。測試句是打字輸入的，有中文也有英文；語音辨識不在這個分數裡。工地模式的保留句在開發擷取器時完全沒用到；
在那裡規則擷取器單獨就有 90 %，所以 LLM 的貢獻是擷取器漏掉的換句話說（兩者結合 95 %）。倉庫的句子由一位撰寫者
和一位審查者撰寫並標註，兩者都是從沒看過解析器程式碼的 AI 代理。我們報告的是他們第一組保留句的第一次（盲測）
量測：加上檢查器是 84 %。這次量測暴露出一些說法上的漏洞，我們之後修正了，所以這組已經不算乾淨。接著由新的一組
盲測 AI 代理（一位撰寫者、一位審查者）寫了全新一組，從沒用來調整過：用修正後的解析器是 88 %。在倉庫的兩組上，
只用 LLM 停在 16–24 %，只用規則擷取器是 68–80 %。我們上線的是兩者的結合，而且每條規則生效前都由安全主管確認。

### 8 · report：The daily report: code counts, the LLM plans（每日報告：程式計數，LLM 規劃）

*投影片上：* 三個步驟（數字、表格與摘要由警報紀錄計算；LLM 只看到發生過的（攝影機、問題）組合，每類各三項
審核過的措施；它以 JSON schema 回傳問題與措施編號）。表格「20 synthetic days · 2 blind AI judges per action」
（20 天合成資料，每項措施兩位 AI 盲評），下方說明：評審是 AI 代理，不知道措施由哪種方法寫成，在「指錯問題」上
177 項中有 176 項意見一致；中間那列的 57 項措施中有 14 項改用了範本文字。評審是 AI 代理，不是真人；報告這頁時
要講清楚。

| 措施的產生方式 | 指錯問題（兩位評審皆判定） | 合理（兩位評審皆判定） |
|---|---|---|
| LLM 自由撰寫措施 | 20.0 % | 45.0 % |
| LLM 挑問題、自己寫措施（有關鍵字檢查） | 3.5 % | 52.6 % |
| LLM 挑問題並選一項審核過的措施（目前採用） | 0.0 % | 100.0 % |

目前採用的設計中，每項措施的文字是我們寫的（審核過），所以它的「合理」只評問題與措施的選擇（投影片上以 * 標示）。
頁尾：PC GPU 上的 Qwen2.5-1.5B、`docs/results/report_actions_judged.json`、`report_actions_judging/`（腳本：
`scripts/eval_report.py`）。

測試時，讓 1.5B 模型自己寫整份報告，會把數字算到錯的對象上，還會自創用語。所以目前的設計把工作拆開：每個
數字、表格和摘要都由程式從警報紀錄計算；模型只看到實際發生過的攝影機與問題組合，每組附三項針對這類問題、
審核過的措施，並以編號回答。它不可能點名一支沒出問題的攝影機、編造數字，或拿安全帽去解決人員擁擠的問題。
這份規劃沒有人確認，這正是模型只能「選」的原因。我們在 20 天的合成資料上測試，每項措施由兩位獨立的 AI 評審
代理在不知道是哪種方法寫的情況下評分；在「是否指錯問題」這點上，177 項措施中有 176 項兩位評審意見一致。目前
設計的 100 %「合理」只評選擇，因為措施是我們寫的。LLM 離線或回答無效時，改由範本產生措施，所以報告一定產得出來。

### 9 · falsealarm：A second opinion before anyone is paged（通知任何人之前先複核）

*投影片上：* 三道關卡：持續時間、去重複、是非判斷複核；95.7 % 有戴安全帽的裁切圖被正確放行（作為錯誤「沒戴
安全帽」標記的替代指標）、94.9 % 的違規被確認、在 PC 上每次複核 15.2 ms；被濾掉的警報從不刪除。頁尾：
`scripts/train_probe.py`、`docs/results/probe_train.json`。

安全帽警報確認前要經過三道關卡。第一，沒戴安全帽要持續兩秒，而且每個追蹤目標保留一小段標籤紀錄，單張影格

### 12 · sitelimits：Where it works, and the spec that follows（在哪裡有效，以及由此而來的部署規格）

量化並檢查過：用 INT8 特徵重新訓練 2×512 判斷層後，是非判斷複核維持 95.3 % 準確率（違規保留 93.9 %）；直接沿用
PC 的判斷層則是 94.3 %。LLM 透過 Ollama API 呼叫，而 hailo-ollama 提供同樣的 API，所以搬到 UGen300 應該只需要改
`llm.base_url`。Stage II 會在實機上確認這點並量測 Hailo 版本，它的準確率可能和我們在 PC 上量的 Ollama 版本不同。
UGen300 的數字是依 Hailo 公開數據推算的估計值，不是量測結果。語言模型只在需要時執行；偵測器每張影格都跑，
是非判斷複核則每則安全帽警報跑一次。

### 19 · risks：What could go wrong, and the plan（可能出什麼問題，以及對策）

*投影片上：* 六項風險與對策的表格。頁尾：測試數據來自 `docs/results/probe_train.json`、`rule_parsing*.json`、
`site_eval_warehouse_018/019.json`。

| 風險 | 對策 |
|---|---|
| USB 吞吐量低於 Hailo 的 PCIe 參考值；倉庫模式負載尚未量測 | 兩者都在第 1 週量測；batch 8；必要時每支攝影機每秒 5 張影格 |
| 小 LLM 誤解規則，或離線 | 檢查器（規則擷取器）覆寫它找到的數字、時間和物件；安全主管確認；擷取器單獨在保留集上 90 %（工地模式）/ 68 %（倉庫） |
| 是非判斷複核濾掉真實違規（PC 測試中 5 %：1 − 0.949，`probe_train.json`） | 被濾掉的警報保留並以淡色顯示 |
| 某些建築裡漏掉堆高機（W018 和 W019 只在 17 % 和 12 % 的堆高機影格中偵測到；原因尚未查明） | 用客戶自己的車輛微調倉庫偵測器（需要多少資料會在 Stage II 量測） |
| 大廠房、距離很遠的攝影機 | 涵蓋規格：每個最多 12 支攝影機的場區一台設備；每個監看區域都要被兩支以上攝影機看到 |
| 偵測器和生成式 AI 共用一顆加速器 | 生成式 AI 只在需要時執行；HailoRT 排程負載在第 3 週量測 |

每個尚未解決的風險都有量測計畫和備案。設備端的風險是在 PC 上無法解決的：USB 吞吐量、倉庫模式的負載，以及偵測器
和生成式 AI 共用一顆加速器，都會在 Stage II 量測，備案是 batch 8、每支攝影機每秒 5 張影格，以及只在需要時才執行
生成式 AI。模型端的風險已經由設計處理：檢查器和安全主管會攔下誤解的規則，被濾掉的警報仍然看得到，部署規格則讓
大廠房維持在我們量測過的涵蓋範圍內。堆高機漏偵測是 Stage I 唯一無法修正的偵測器限制，因為在測試建築上重新訓練，
就會用掉一個測試場景。我們還沒查明原因，微調需要多少客戶資料也還沒量測。

## 要準備的問題

- **倉庫影片是真的嗎？** 不是，是合成影片：NVIDIA PhysicalAI-SmartSpaces（CC BY 4.0）。選它是因為它有同步、校正過的
  攝影機，還有每個人在地面上位置的真值，這樣才能量測。Stage II 會在測試場地校正真實的多鏡頭平面圖。工地模式
  （安全帽）的素材是 Mixkit 免費影片。
- **為什麼不用更大的模型，或全部交給 VLM？** Hailo 有公開這個 1.5B 模型的 Hailo-10H 版本（7.35 tokens/s）；和偵測器
  一起跑的情況會在 Stage II 量測，我們估計在 UGen300 上每條規則約 11.3 秒。檢查器加上安全主管確認讓它變得可用（打字輸入
  的保留測試句，工地模式 40 % → 95 %、倉庫模式 16–24 % → 84–88 %，在 PC 上用 Ollama 量測）。是非問題不需要
  生成式模型：CLIP 判斷層的測試準確率 95.3 %，每張裁切圖 15.2 ms（`probe_train.json`）。
- **LLM 答錯或離線怎麼辦？** 檢查器會覆寫它在句子裡找到的數字、時間和物件並顯示備註，安全主管確認後規則才生效。
  離線時由規則擷取器單獨解析規則（工地模式保留集 90 %，全新倉庫保留集 68 %），報告則改用範本。
- **有沒有在測試場景上調參數？** 偵測器和信心度設定沒有：信心度與距離設定都在驗證場景 W020 上決定。兩項警報邏輯
  修正是在我們看過測試場景的凍結版本之後，在開發與驗證場景（W009、W012、W017、W020）上開發的，而 W017 是測試
  場景 W018 的雙胞胎場景。W010 是 demo 場景：追蹤器是看著它開發的，它用的是 demo 的區域。其他五個測試場景的區域
  由 AI 代理在任何結果出來前、依攝影機涵蓋地圖畫出。不用掉一個測試場景就無法重新訓練偵測器，所以我們沒有重新訓練。
  凍結版本（較乾淨的保留測試結果）和最終版本的結果都有公開。
- **還有什麼沒量測？** UGen300 實機上的吞吐量、延遲與功耗，包括倉庫模式的負載（Stage II）。用 Hailo 版
  Qwen2.5-1.5B 時的規則解析與報告準確率。錄音語音規則的語音辨識準確率（規則測試句是打字輸入的）。開放詞彙偵測的
  準確率，以及工地模式（安全帽）以頭部大小估算的距離。臉部馬賽克漏掉人的頻率。真實（非合成）倉庫影片。倉庫偵測器
  HEF 尚未編譯。長時間的身分一致性：編號幾十秒內就會改變，所以不顯示。
- **一台設備可以接幾支攝影機？** 每個最多 12 支攝影機的場區一台 UGen300，這是由倉庫測試場景得出的涵蓋規格。
  工地模式（安全帽）十支攝影機、每支目標每秒十張影格，估計用到一台 UGen300 的 40 %（以名目上每秒 100 張影格計）。
  倉庫模式的負載會在 Stage II 第 1 週量測。
