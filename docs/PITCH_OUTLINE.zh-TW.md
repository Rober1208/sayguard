## 貫穿整份簡報的主線：本地 LLM 用來做什麼

評審會看到很多偵測模型；SayGuard 的不同之處，在於它怎麼運用一個小型本地 LLM（Qwen2.5-1.5B-Instruct，以 Ollama API 呼叫）。Stage I 由 Ollama 在 PC 的 GPU 上執行；Stage II 搬到 UGen300，由 hailo-ollama 提供同一套 API。LLM 負責兩件偵測模型做不到的事，原則就是第 5 頁的標題：**LLM 起草、程式把關、工安人員確認。** 規則完全照這個原則運作。日報規劃沒有人確認，所以 LLM 在這裡只能「選」：問題只能從實際發生過的問題裡選，措施只能從事先審過的清單裡選。

1. **把一句話變成規則，而且聽得懂現場的說法。** 模型依 SayGuard 規則模型產生的 JSON schema 填欄位，接著由固定邏輯的檢查器，用它在句子裡找到的數字、距離、時間、持續時間和物件覆寫模型的結果。檢查器可能漏掉某些說法，這也是規則生效前要先讓工安人員看過白話版內容的原因之一。在打字輸入的保留測試句上（看規則是否完全正確，不含語音辨識），工地模式從只靠 LLM 的 40 % 提升到加上檢查器後的 95 %；倉庫模式在第一組盲測句的第一次測試從 16 % 提升到 84 %，在全新的第二組則從 24 % 提升到 88 %。語言能力也屬於這項工作：規則可以用國語或英文說；Whisper 會先拿到現場的區域和攝影機名稱作為提示，LLM 也會拿到中英文兩種區域名稱。區域名稱裡的數字不管寫成阿拉伯數字、中文數字或英文（七號走道、7號走道、aisle seven），後面有沒有「區」，檢查器都認得。簡體中文的輸出會轉成台灣繁體用語。語言能力只在規則測試裡一併量測：每一組測試句都混合了國語和英文。在 PC 上解析一條規則平均 0.35–0.40 秒（保留測試集最長 0.64 秒）。LLM 離線時，檢查器所用的固定邏輯規則擷取程式也能單獨解析規則：工地模式保留測試集 90 %，倉庫全新測試集 68 %。不過在倉庫那組句子裡，有好幾種換句話說的講法，只靠擷取程式完全解析不出規則，經過檢查的 LLM 草稿卻是對的，這就是 LLM 要留在流程裡的原因。
2. **規劃工安日報。** 所有數字、表格和摘要都由程式計算。模型只看得到實際發生過的（攝影機、問題）組合，每組附三項事先審過的改善措施，並依 JSON schema 回傳問題和措施的編號，所以它不可能點名一支沒出問題的攝影機，也不可能編造數字。每項措施由兩位 AI 評審盲評：讓模型自由撰寫時，有 20.0 % 的措施配錯問題；由模型挑問題、自己寫措施（加關鍵字檢查）時是 3.5 %；目前的設計是 0.0 %。

所有 LLM 準確率都是在 PC 的 GPU 上以 Ollama 的 qwen2.5:1.5b 量測。同一模型的 Hailo GenAI 版本量化方式不同，尚未量測。LLM 只在需要時執行（新增規則或產生日報），不會每張畫面都和偵測模型搶運算資源。Hailo GenAI Model Zoo 列出 Qwen2.5-1.5B-Instruct 在 Hailo-10H 上為 7.35 tokens/s，0.37 秒開始輸出。依這些數字，`docs/results/benchmark.md` 估計在 UGen300 上從說出規則到產生規則 JSON 約 11.3 秒，Whisper 轉寫一段 5 秒的規則約 2.4 秒（估計值，未實測）。這條主線涵蓋簡報第 5–8 頁，示範影片也會展示這兩項工作。

## 逐頁說明

### 1 · cover：SayGuard

*投影片上：* 上方標籤「ASUS UGEN AI LEAGUE · STAGE I PROPOSAL」；「One UGen300 per site area. Every camera watched. Rules you can say.」（每個區域一台 UGen300，每支攝影機都有人顧，規則用說的就能加）；標籤「Battlefield Lightning · UGen300」、「Workplace AI」、「[Team name] · [Onsite / Global Online track]」。

SayGuard 是一套工安助手，顧好一個區域內的所有攝影機，用講的就能設定。它有兩種模式：工地模式檢查每支攝影機裡的人有沒有戴安全帽；倉庫模式把所有攝影機整合成一張平面圖。我們展示的每個結果，都是在實際可運作的 Stage I 原型上量到的，原型跑在 PC 的 GPU 上；Stage II 會搬到 ASUS UGen300，每個區域一台。在 Stage II 實機量測之前，UGen300 的數字都是依 Hailo 公開數據推算的估計值。

### 2 · problem：Sites have cameras. Few have anyone watching them live.（現場都有攝影機，卻很少有人即時在看）

*投影片上：* 三張卡片：「Found too late」（發現得太晚：沒戴安全帽，可能要等出事後翻錄影才發現）；「Rules are fixed」（規則寫死：許多 AI 攝影機出廠就是一份固定的規則清單，想新增區域、距離、人數或時段規則，就得手動重新設定）；「Alarms get ignored」（警報沒人理：誤報一多就失去信任，而把現場影片傳上雲端，又有隱私和頻寬的顧慮）。

這頁講三個問題。第一，很少有現場有人即時盯著攝影機，所以沒戴安全帽，可能要等出事後翻錄影才發現。第二，許多 AI 攝影機出廠就是一份固定的規則清單，而且要一支一支設定，想新增一個區域、距離、人數或時段規則，都得手動重新設定。第三，警報常常出錯，大家就不再信任、不再理會；改把現場影片傳上雲端，又會有隱私和頻寬的顧慮。

### 3 · idea：One box next to the recorder. Every camera covered.（錄影主機旁一台盒子，顧好每支攝影機）

*投影片上：* 流程：現場原有的攝影機（RTSP；只在監看區域不到兩支攝影機拍得到的地方補裝；不上雲）→ 主機 + ASUS UGen300（批次處理的偵測模型、CLIP 是非判斷複核、Whisper 和 Qwen2.5，全部在現場執行：目前在 PC 的 GPU 上，Stage II 在 UGen300 上）→ 工安人員（經過複核的警報、即時平面圖、工安日報、用說的加規則）。兩張模式卡片：「Hard-hat mode: construction sites, hard hats on every camera」（工地模式：每支攝影機都檢查安全帽）與「Warehouse mode: all cameras fused on one floor plan, zones and forklift distances in metres」（倉庫模式：所有攝影機整合成一張平面圖，管制區和堆高機距離都用公尺算）。

一張圖講完整個產品。現場保留原有的攝影機，只在監看區域不到兩支攝影機拍得到的地方補一支。我們在錄影主機旁加一台小主機和一台 UGen300。所有模型都在現場執行：Stage I 原型在 PC 的 GPU 上，Stage II 在 UGen300 上。工安人員會收到經過複核的警報、即時平面圖和工安日報，還能用說的加規則。兩種模式共用同一套流程，差別只在看什麼：工地模式逐支攝影機檢查安全帽，倉庫模式則在同一張平面圖上看人和車。

### 4 · demo：The working prototype（實際可運作的原型）

*投影片上：* 工地模式儀表板截圖；說明文字「10 looping demo streams, analysed live · alerts double-checked locally · spoken rules · PC GPU today, UGen300 in Stage II」（10 路示範串流循環播放、即時分析；警報在本地複核；用說的加規則；目前在 PC GPU 上，Stage II 換成 UGen300）。

這是實際的儀表板畫面（截圖尺寸 1920 × 1080），十路示範串流循環播放，每路以每秒十張畫面為目標即時分析。紅框是沒戴安全帽的人，臉部在本地就打上馬賽克。每則警報都附上複核結果；工安人員在右側說出或打字輸入規則，確認後就生效。同一套軟體目前跑在 PC 的 GPU 上，Stage II 會搬到 UGen300。

### 5 · llm：A small LLM proposes. Code checks. The officer confirms each rule.（小 LLM 起草，程式把關，每條規則由工安人員確認）

*投影片上：* 上方標籤「INNOVATION · THE LOCAL LLM · TWO JOBS」（創新 · 本地 LLM · 兩項工作）。工作 1「Turns a sentence into a rule」（一句話變成規則）：工地模式 40 % → 95 %，倉庫模式 16–24 % → 84–88 %（打字輸入的保留測試句，只靠 LLM → 加上檢查器；只靠檢查器是 90 % / 68–80 %）。工作 2「Plans the daily report」（規劃工安日報）：措施配錯問題 20 % → 0 %（自由撰寫 → 從事先審過的措施中挑選，兩位 AI 盲評）。第三張卡片「Speaks like the site」（聽得懂現場的話）講的是兩項工作共通的語言能力，不是第三項工作：國語或英文、台灣用語、區域名稱照大家平常的叫法（「七號走道」、「aisle seven」）；LLM 離線時，只靠檢查器仍能解析 68–90 % 的打字保留測試句。下方橫條：「…after 10 pm」→ LLM 22:00–00:00 → 檢查器 22:00–06:00。頁尾：在 PC GPU 上以 Ollama 執行 Qwen2.5-1.5B-Instruct 量測；UGen300 版本（hailo-ollama）尚未量測。

這是我們最主要的創新。15 億參數的模型還不夠可靠，不能單獨信任，所以我們從不讓它自己做決定。Hailo 已公開這個模型的 Hailo-10H 版本（7.35 tokens/s）；和偵測模型同時執行的情況會在 Stage II 量測。這個模型有兩項工作。第一，把一句話變成規則，國語或英文都行，區域名稱也照現場的叫法：句子裡明確講到的數字、時間和物件，由固定邏輯的程式覆寫，最後再由工安人員確認。在打字輸入的保留測試句上，這讓工地模式的正確率從 40 % 提升到 95 %，倉庫模式從 16–24 % 提升到 84–88 %。常見的說法只靠檢查器就能處理（90 % / 68–80 %），模型則補上它漏掉的換句話說。第二，規劃工安日報：所有數字都由程式計算，模型只挑出最重要的三個問題，並替每個問題選一項事先審過的改善措施。這份規劃沒有人確認，所以模型只能從清單裡選。兩位 AI 評審盲評的結果，它挑的措施沒有一項配錯問題；讓它自由撰寫時則有 20 % 配錯。下方是真實案例：「after 10 pm」，模型給的是 22:00 到 00:00，檢查器套用明訂的慣例，改成 22:00 到 06:00。這些準確率是在 PC 上以 Ollama 量測；Hailo 版本會在 Stage II 量測。

### 6 · voice：Speak a rule, confirm it, it is live（說出規則、確認，馬上生效）

*投影片上：* 四個步驟：說（Whisper-Small，以現場詞彙作為解碼提示）→ 起草（Qwen2.5-1.5B，依固定 schema 輸出 JSON）→ 檢查（固定邏輯的檢查器：覆寫句子裡講到的數字、時間和物件）→ 確認（工安人員看過白話版規則後啟用）；一行說明「LLM offline? The checker's rule extractor alone still parses 68–90 % of typed held-out sentences」（LLM 離線時，只靠檢查器仍能解析 68–90 % 的打字保留測試句）；以及「Say a rule」面板截圖。

流程有四步。Whisper-Small 轉寫國語或英文，並先拿到現場的區域和攝影機名稱作為提示；真人錄音的辨識準確率尚未量測。Qwen2.5-1.5B 依規則模型產生的 JSON schema 填寫，回答直接對應規則本身的欄位。檢查器擷取句子裡明確講到的內容，兩邊不一致時一律以檢查器為準；每次覆寫 LLM 的結果都會留下備註，讓工安人員看到改了什麼；檢查器漏掉的說法，則由工安人員在確認時攔下。對應不到任何攝影機的規則無法啟用。LLM 離線時，只靠檢查器也能解析規則（工地模式保留測試集 90 %，倉庫全新測試集 68 %）。在 PC 上每條規則平均解析 0.35–0.40 秒（最長 0.64 秒）。在 UGen300 上估計每條規則約 11.3 秒，轉寫一段 5 秒的規則另需約 2.4 秒（依 Hailo 公開數據推算的估計值，未實測）。

### 7 · accuracy：With the checker, a 1.5B model gets 84–95 % of held-out rules exactly right（加上檢查器，1.5B 模型在保留測試句上有 84–95 % 的規則完全正確）

*投影片上：* 兩組長條（只靠 LLM / 只靠檢查器 / LLM + 檢查器）。工地模式，20 句打字輸入的保留測試句：40 %、90 %、95 %。倉庫模式，2 × 25 句打字輸入的保留測試句：16–24 %、68–80 %、84–88 %。一行說明：84 % 是第一組的第一次測試，當時還沒修正它暴露出的問題；88 % 是修正後全新的第二組。頁尾：PC GPU 上的 Ollama qwen2.5:1.5b、`scripts/eval_rules.py [--site]`、`docs/results/rule_parsing*.json`。

一條規則要每個標註欄位都對才算正確：規則類型、物件、人數或距離、時段、句中有講到的持續時間，以及涵蓋的攝影機或區域。測試句都是打字輸入，國語和英文都有；語音辨識不算在這個分數裡。開發檢查器時完全沒用到工地模式的保留測試句；在這組句子上，只靠檢查器就有 90 %，所以 LLM 的貢獻是補上檢查器漏掉的換句話說（兩者合起來 95 %）。倉庫的句子由兩個從沒看過解析程式碼的 AI 撰寫並標註（一個撰寫、一個審核）。我們報告的是第一組保留測試句的第一次（盲測）結果：加上檢查器是 84 %。這次測試暴露出一些說法上的漏洞，我們事後補上了，所以這組已不再算盲測。接著由另外兩個 AI（一個撰寫、一個審核）寫出全新的一組，從未用來調整：修正後的解析程式得到 88 %。在倉庫的兩組句子上，只靠 LLM 停在 16–24 %，只靠檢查器是 68–80 %。實際上線的是兩者的組合，每條規則生效前也都由工安人員確認。

### 8 · report：The daily report: code counts, the LLM plans（工安日報：程式算數字，LLM 做規劃）

*投影片上：* 三個步驟（數字、表格和摘要由警報紀錄計算；LLM 只看得到發生過的（攝影機、問題）組合，每類各附三項事先審過的措施；它依 JSON schema 回傳問題和措施的編號）。表格「20 synthetic days · 2 blind AI judges per action」（20 天模擬資料，每項措施兩位 AI 盲評），下方說明：評審是 AI，不知道每項措施出自哪種做法，在「配錯問題」上 177 項有 176 項意見一致；中間那列的 57 項措施裡，有 14 項改用範本文字。報告這頁時要講清楚：評審是 AI，不是真人。

| 措施怎麼產生 | 配錯問題（兩位評審都認為） | 合理（兩位評審都認為） |
|---|---|---|
| LLM 自由撰寫措施 | 20.0 % | 45.0 % |
| LLM 挑問題、自己寫措施（加關鍵字檢查） | 3.5 % | 52.6 % |
| LLM 挑問題並選一項事先審過的措施（目前採用） | 0.0 % | 100.0 % |

目前的設計裡，每項措施的文字都是我們事先寫好、審過的，所以它的「合理」只評問題和措施有沒有挑對（投影片上以 * 標示）。頁尾：PC GPU 上的 Qwen2.5-1.5B、`docs/results/report_actions_judged.json`、`report_actions_judging/`（腳本：`scripts/eval_report.py`）。

測試時發現，讓 1.5B 模型自己寫整份日報，會把數字歸到錯的對象，還會自創用語。所以目前的設計把工作拆開：所有數字、表格和摘要都由程式從警報紀錄算出來；模型只看得到實際發生過的攝影機與問題組合，每組附三項專為這類問題撰寫、事先審過的措施，並用編號回答。它不可能點名一支沒出問題的攝影機、編造數字，或拿安全帽去解決人員擁擠的問題。這份規劃沒有人確認，所以模型只能「選」。我們用 20 天的模擬資料測試，由兩位獨立的 AI 評審在不知道做法的情況下替每項措施評分；在「有沒有配錯問題」上，177 項措施中有 176 項兩位評審意見一致。目前設計的「合理」100 % 只評挑選，因為措施文字是我們寫的。LLM 離線或回答無效時，改由範本產生措施，所以日報一定產得出來。

### 9 · falsealarm：A second opinion before anyone is paged（通知任何人之前，先複核一次）

*投影片上：* 三道關卡：持續時間、去重複、是非判斷複核；正確放行 95.7 % 有戴安全帽的裁切圖（以此代表誤標「沒戴安全帽」的情況）、確認 94.9 % 的違規、PC 上每次複核 15.2 ms；濾掉的警報一律不刪除。頁尾：`scripts/train_probe.py`、`docs/results/probe_train.json`。

安全帽警報確認前要過三道關卡。第一，沒戴安全帽要持續兩秒，而且每個追蹤目標會保留一小段標籤紀錄，單張畫面判錯不會觸發警報。第二，同一支攝影機上同一個人的重複警報只算一次。第三，複核只看標記頭部周圍的裁切畫面。「這個人有沒有戴安全帽？」是一個判斷，不是對話，所以不需要生成式模型：凍結的 CLIP ViT-B/32 影像編碼器加上 2×512 的分類頭，在 94 張有戴安全帽的保留裁切圖中正確放行 95.7 %（這些是資料集裡標好的裁切圖，用來代表誤標「沒戴安全帽」的情況），並確認 94.9 % 的真實違規（99 張沒戴的保留裁切圖），整體測試準確率 95.3 %（`probe_train.json`）。在 PC 上每張裁切圖 15.2 ms。因為複核仍會濾掉約 5 % 的真實違規（1 − 0.949），所以濾掉的警報一律不刪除，而是變暗留在清單裡供人檢視。視覺語言模型仍可作為選項（`verifier.backend: vlm`）。

### 10 · site：Every camera on one floor plan（所有攝影機整合在一張平面圖上）

*投影片上：* 倉庫模式儀表板截圖和幾個重點：每個人只算一次，而不是每支攝影機各算一次；管制區畫在平面圖上，和堆高機的距離用公尺算；每個人每次進入只發一則警報，而不是每支攝影機各一則，並在每一支拍到他的攝影機畫面上標出來；規則用區域名稱來說。頁尾：`docs/results/site_eval.json`、合成倉庫，NVIDIA PhysicalAI-SmartSpaces（CC BY 4.0）。

多鏡頭整合在倉庫模式最能發揮作用。每支攝影機都有校正資料，把地面對應到畫面上，所以每個偵測結果都能換算成同一張平面圖上的位置。這裡用的是示範場景 Warehouse_010：NVIDIA 合成倉庫中的十一支同步攝影機。現場平均有 24.97 人，SayGuard 算出 26.56 人，把各攝影機人數直接相加則是 51.64 人。管制區只要在平面圖上畫一次，不必每支攝影機各畫一次。人和堆高機的距離用公尺量，這個場景的誤差中位數是 0.2 m。每個人每次進入只發一則警報，而不是每支攝影機各一則，並在每一支拍到他的攝影機畫面上標出來；規則裡的區域名稱照大家平常的叫法。畫面上不顯示人員編號：編號幾十秒內就會換（Warehouse_010 的 5 分鐘片段中，每人平均 10.7 個編號），顯示出來反而會誤導。

### 11 · siteevidence：Six buildings the detector never trained on（六棟偵測模型沒訓練過的建築）

*投影片上：* 一行測試方式與注意事項（偵測模型與信心門檻在驗證場景上決定；管制區由 AI 在看到結果前畫好，示範場景 W010 除外；W017 和 W018 是同一棟建築、同一組鏡頭）；表格（規則類型 · 涵蓋 · 自己的警報 · 誤報 · 凍結版：涵蓋 · 誤報）；人數誤差（整合後對照直接相加）；一段說明，包括「涵蓋」的定義、堆高機的冷卻時間，以及兩項警報邏輯修正。頁尾：`scripts/eval_site.py`、`docs/results/site_eval*.json`、`site_by_zone_kind.json`、`docs/results/frozen/`。

最終版（兩項警報邏輯修正之後）。「涵蓋」＝事件有自己的警報，或落在同一人前一則警報的冷卻時間內；「自己的警報」＝嚴格召回率。

| 規則類型（6 個測試場景） | 涵蓋事件 | 自己的警報（嚴格召回率） | 誤報 |
|---|---|---|---|
| 門口與碼頭區 | 53 / 53（100 %） | 52 / 53（98 %） | 0 / 52 |
| 堆高機 3 公尺規則 | 56 / 61（92 %） | 25 / 61（41 %） | 1 / 26 |
| 窄走道 | 98 / 118（83 %） | 71 / 118（60 %） | 3 / 77（4 %） |

凍結版（兩項修正之前；偵測模型和信心門檻相同，是更接近盲測的保留測試結果）：

| 規則類型 | 涵蓋事件 | 自己的警報（嚴格召回率） | 誤報 |
|---|---|---|---|
| 門口與碼頭區 | 50 / 53（94 %） | 49 % | 0 / 26 |
| 堆高機 3 公尺規則 | 54 / 61（89 %） | 38 % | 1 / 24 |
| 窄走道 | 76 / 118（64 %） | 33 % | 1 / 40 |
| 作業區 | 281 / 338（83 %） | 43 % | 16 / 244 |
| 其他區域 | 34 / 48（71 %） | 44 % | 4 / 30 |

這頁的重點是測試方式，以及它的限制。六個測試場景（W010、W013、W015、W018、W019、W022）和訓練場景是不同的建築，偵測模型沒用它們訓練過。其中兩個不算完全獨立：W010 是我們的示範場景，追蹤器是看著它開發的，管制區也直接取自示範設定檔，而不是事先盲畫；開發場景 W017 和測試場景 W018 是同一個空間、同一組攝影機。信心門檻和距離參數在驗證場景 W020 上決定。其他五個測試場景的管制區，由只看過各場景鏡頭覆蓋圖的 AI 在看到任何結果之前畫好。只要 SayGuard 對某個事件發出了自己的警報，或該工人當時仍在先前警報的冷卻時間內，就算涵蓋；嚴格召回率只算自己的警報。堆高機規則的嚴格召回率只有 41 %，是刻意設計的結果：60 秒的冷卻時間，就是為了不對在停放堆高機 3 公尺邊緣進進出出的人重複發警報。不屬於以上四類的區域（「其他」）誤報率最高，44 則中有 6 則（14 %）。

主要數字取自兩項警報邏輯修正後的最終版。這兩項修正是我們看過測試場景的凍結版結果之後，在開發與驗證場景（W009、W012、W017、W020）上開發的。凍結版用的是相同的偵測模型和信心門檻，更接近盲測：涵蓋了 94 % 的門口事件、89 % 的堆高機事件、64 % 的走道事件、83 % 的作業區事件和 71 % 的其他區域事件。修正也讓誤報變多：作業區從 244 則中 16 則增加到 362 則中 26 則，走道從 40 則中 1 則增加到 77 則中 3 則。六個場景的人數誤差，整合後是 0.05 到 1.74 人，各攝影機直接相加則是 1.76 到 60.09 人。兩次結果都放在 repo 裡。

### 12 · sitelimits：Where it works, and the spec that follows（在哪裡有效，以及由此訂出的部署規格）

*投影片上：* 鏡頭覆蓋圖（橘色＝一支攝影機，綠色＝兩支以上攝影機看得到身高 ≥ 40 px 的人）。Warehouse_010：11 支攝影機，地面都有兩支以上拍到，堆高機規則涵蓋 95 %、43 % 有自己的警報、沒有誤報。Warehouse_020：16 支攝影機，中間有死角，堆高機規則涵蓋 57 %、34 % 有自己的警報、51 則警報中 16 則誤報。一行「Coverage is the clearest difference, not a proven cause」（鏡頭覆蓋是最明顯的差別，但還沒證明是原因）。三項限制（某些建築漏掉堆高機、不顯示人員編號、超過 12 支攝影機），以及規格「Coverage spec: one UGen300 per area of ≤ 12 cameras · watched zones seen by ≥ 2 cameras at ≥ 40 px」（部署規格：每個 ≤ 12 支攝影機的區域一台 UGen300；監看的管制區要有 ≥ 2 支攝影機拍到，人員身高 ≥ 40 px）。

鏡頭覆蓋是這兩個場景之間最明顯的差別，但我們還沒證明它就是原因。Warehouse_010 幾乎整片地面都有兩支以上攝影機拍到，堆高機規則在這裡涵蓋了 95 % 的事件（43 % 有自己的警報，其餘落在冷卻時間內），而且沒有誤報。驗證場景 Warehouse_020 是一座大廠房，16 支攝影機之間有很大的死角；在那裡，堆高機規則只涵蓋 57 % 的事件（34 % 有自己的警報），51 則警報中有 16 則誤報。W020 還有其他差異：人數大約是兩倍（平均 49.02 人對 24.97 人）、攝影機數超出規格，而且和訓練場景 W000–W007 是同一棟建築。在這個場景上，身高 20–40 px 的人偵測率是 68 %，40–80 px 則是 92 %，40 px 的門檻就是這樣來的。另外還有兩項限制：W010 有 98.6 % 的堆高機畫面偵測到堆高機，但 W018 只有 16.9 %、W019 只有 11.5 %（W022 是 79.3 %），原因還沒查明；人員編號幾十秒內就會換（W010 上 5 分鐘內每人平均 10.7 個編號），所以不顯示。部署規格就是根據鏡頭覆蓋訂出來的：每個最多 12 支攝影機的區域放一台 UGen300，每個監看的管制區都要有至少兩支攝影機拍到、人員身高 40 px 以上。12 支攝影機是由測試場景訂出的覆蓋規格；倉庫模式在 UGen300 上的運算負載尚未量測（Stage II 第 1 週）。

### 13 · detector：Detectors trained where it matters（關鍵的地方用專門訓練的偵測模型）

*投影片上：* 三張卡片，各有一個數字：安全帽（mAP50 0.939；Hailo 模擬器是另一種評估：INT8 0.889 對浮點 0.893）；倉庫物件（找到 12–99 % 的堆高機畫面：W010 99 %、W022 79 %、W018 17 %、W019 12 %）；規則提到的其他物件（YOLO-World 在 Warehouse_010 的 30 個標註堆高機框中一個都沒找到；挖土機警報僅供示範，準確率未量測），以及挖土機的小截圖。頁尾：`docs/results/detector_metrics.json`、`hailo_int8.json`、`site_eval*.json`。

SayGuard 用三種偵測模型，各用在需要的地方。**安全帽：** 用 Roboflow Hard Hats v2（CC BY 4.0）微調的 YOLOv8s，在 2,001 張沒看過的測試圖片上 mAP50 為 0.9393，違規類別（沒戴安全帽的頭）召回率 0.9008。它已經編譯成 Hailo-10H 的 HEF，但還沒在硬體上跑過。在 Hailo 的 bit-exact 模擬器（逐位元重現晶片運算）裡，INT8 模型的 mAP50 是 0.889，浮點版是 0.8927，兩者用同一種方式量測。0.9393 是 Ultralytics 自己的評估程式算的，評估方式不同，所以 0.889 只能和 0.8927 比較。**倉庫物件：** 六類的 YOLOv8s（人、堆高機、托板車、搬運車、移動機器人、人形機器人），用 5 棟建築、8 個合成訓練場景的 8,000 張圖片，以 960 px 微調，沒用到任何評估場景。它在 Warehouse_010 有 98.6 % 的堆高機畫面找到堆高機，但在 W018 只有 16.9 %、W019 只有 11.5 %、W022 是 79.3 %，原因還沒查明。機器人有自己的類別，不會和工人混在一起算。**規則提到的其他物件：** 用 YOLO-World，只要給出物件名稱就能偵測，挖土機示範就是這樣做的；開放詞彙偵測的準確率尚未量測。在合成倉庫上，YOLO-World 在 30 個堆高機框中一個都沒找到，COCO YOLOv8s 只把其中 7 個認成「truck」，還把 39 % 的人形機器人當成人。所以現場倚賴的類別交給專門訓練的偵測模型，其他物件再交給開放詞彙偵測。

### 14 · privacy：Video never leaves the site.（影像不出現場）

*投影片上：* 以強調色為底的聲明頁。

隱私是從一開始就設計進去的，不是事後補上。偵測、語音、語言模型和複核，所有模型都在現場執行：目前在 PC 的 GPU 上，Stage II 在 UGen300 上。每個畫面和快照裡，偵測到的人員框都會把臉部打上馬賽克；用的是偵測模型本來就找到的框，不需要額外的模型。偵測模型漏掉的人不會打上馬賽克，漏掉的比例尚未量測。系統只儲存事件快照，預設 14 天後刪除（設定檔中的 `retention_days`）。倉庫模式不顯示任何人員編號。

### 15 · hardware：One 2.5 W accelerator per site area（每個區域一顆 2.5 W 加速器）

*投影片上：* 流程：IP 攝影機 / NVR → 主機 → ASUS UGen300 → 工安人員。兩個方塊：Stage I 原型（PC GPU、工地模式：十支攝影機、每支目標每秒 10 張畫面，經同一個批次偵測模型實測每秒約 105 張；以名目上的每秒 100 張估算，約用掉一台 UGen300 的 40 %）與 Stage II（偵測模型和生成式 AI 搬到 UGen300；每個 ≤ 12 支攝影機的區域一台，這是覆蓋規格；倉庫模式的負載在第 1 週量測）。頁尾：UGen300 規格取自 ASUS 產品規格書；負載估計取自 `docs/results/benchmark.md`。

這張表就是可行性的依據：每項工作都對應到 Hailo 已為 Hailo-10H 公開、並附處理量數據的模型。目前只有一個網路完成編譯：安全帽偵測模型已經編譯成 HEF，但還沒在硬體上跑過。在 Hailo 的 bit-exact 模擬器裡，它的 INT8 模型 mAP50 是 0.889，浮點版是 0.8927（只能比較這兩個數字；PC 上的 0.9393 是另一種評估）。CLIP 影像編碼器也在同一個模擬器裡量化並檢查過：用 INT8 特徵重新訓練 2×512 分類頭後，複核仍維持 95.3 % 準確率（違規保留率 93.9 %）；PC 的分類頭直接套用在 INT8 特徵上則是 94.3 %。LLM 以 Ollama API 呼叫，而 hailo-ollama 提供同一套 API，所以搬到 UGen300 應該只要改 `llm.base_url`。Stage II 會在實機上確認這一點，並量測 Hailo 版本；它的準確率可能和我們在 PC 上量測的 Ollama 版本不同。UGen300 的數字都是依 Hailo 公開數據推算的估計值，不是量測結果。語言模型只在需要時執行；偵測模型每張畫面都跑，複核則是每則安全帽警報跑一次。

*投影片上：* 六項風險與對策的表格。頁尾：測試數據取自 `docs/results/probe_train.json`、`rule_parsing*.json`、`site_eval_warehouse_018/019.json`。

## 要準備的問題

- **倉庫影片是真的嗎？** 不是，是合成影片：NVIDIA PhysicalAI-SmartSpaces（CC BY 4.0）。選它是因為攝影機同步且校正過，還有每個人在地面上真實位置的標準答案，這樣才能量測。Stage II 會在測試場地校正真實的多鏡頭平面圖。工地模式的素材是 Mixkit 免費影片。
- **為什麼不用更大的模型，或全部交給 VLM？** Hailo 已經公開這個 1.5B 模型的 Hailo-10H 版本（7.35 tokens/s）；和偵測模型同時執行的情況會在 Stage II 量測，我們估計在 UGen300 上每條規則約 11.3 秒。加上檢查器和工安人員確認，它就夠用了（打字輸入的保留測試句，工地模式 40 % → 95 %、倉庫模式 16–24 % → 84–88 %，在 PC 上以 Ollama 量測）。是非題不需要生成式模型：CLIP 分類頭的測試準確率 95.3 %，每張裁切圖 15.2 ms（`probe_train.json`）。
- **LLM 答錯或離線怎麼辦？** 檢查器會覆寫句子裡講到的數字、時間和物件，並顯示備註；規則要經工安人員確認才生效。離線時只靠檢查器解析規則（工地模式保留測試集 90 %，倉庫全新測試集 68 %），日報則改用範本。
- **有沒有在測試場景上調參數？** 偵測模型和信心門檻沒有：信心門檻和距離參數都是在驗證場景 W020 上決定的。兩項警報邏輯修正，是我們看過測試場景的凍結版結果之後，在開發與驗證場景（W009、W012、W017、W020）上開發的，而 W017 和測試場景 W018 是同一棟建築、同一組鏡頭。W010 是示範場景：追蹤器是看著它開發的，管制區也沿用示範設定。其他五個測試場景的管制區，由 AI 在看到任何結果之前，依鏡頭覆蓋圖畫好。要重新訓練偵測模型，就得用掉一個測試場景，所以我們沒有重新訓練。凍結版（更接近盲測的保留測試結果）和最終版的結果都有公開。
- **還有哪些項目尚未量測？** UGen300 實機上的處理量、延遲和功耗，包括倉庫模式的負載（Stage II）。用 Hailo 版 Qwen2.5-1.5B 時的規則解析和日報準確率。真人錄音的語音辨識準確率（規則測試句是打字輸入的）。開放詞彙偵測的準確率，以及工地模式用頭部大小估算的距離。人臉馬賽克漏打的比例。真實（非合成）的倉庫影片。倉庫偵測模型的 HEF（尚未編譯）。長時間的身分一致性：編號幾十秒內就會換，所以不顯示。
- **一台盒子可以接幾支攝影機？** 每個最多 12 支攝影機的區域一台 UGen300，這是由倉庫測試場景訂出的覆蓋規格。工地模式十支攝影機、每支目標每秒十張畫面，估計約用掉一台 UGen300 的 40 %（以名目上的每秒 100 張計）。倉庫模式的負載會在 Stage II 第 1 週量測。
