# 把 SayGuard 搬上 UGen300

**SayGuard 的每個模型，都是因為 Hailo-10H 已經能跑才選的。Stage II 是移植，不是重做。**

PC 原型和 UGen300 版本的架構相同：主機（迷你電腦）負責解碼攝影機串流、追蹤人員、整合平面圖、執行規則引擎和儀表板；神經網路全部交給 UGen300。Stage I 全部在 PC 的 GPU 上執行，還沒有在 UGen300 實機上跑過；不過安全帽偵測模型和複核用的 CLIP 影像編碼器，都已經走過 Hailo 官方的工具鏈，INT8 的準確率也確認過了。

## 為什麼選這些模型

| SayGuard 裡的工作 | 模型 | Hailo-10H 參考效能 |
|---|---|---|
| 在每支鏡頭裡找出人、安全帽和車輛 | YOLOv8s 微調（工地 2 類、倉庫 6 類） | batch 1 為 166 FPS，batch 8 為 252 FPS |
| 複核每一則安全帽警報 | CLIP ViT-B/32 影像編碼器，加上小型是非分類頭 | 81.5 FPS（batch 1） |
| 找出口述規則裡講到的物件（挖土機、堆高機…） | YOLO-World v2-S | 46.6 FPS |
| 語音轉文字 | Whisper-Small | 每秒 10.6 個 token |
| 把一句話變成規則、規劃日報 | Qwen2.5-1.5B-Instruct | 每秒 7.35 個 token，約 0.37 秒開始回應 |

參考效能取自 Hailo Model Zoo 和 Hailo GenAI Model Zoo。

- **一個 YOLOv8s 看全部鏡頭**：所有串流的畫面打包成一批，送進同一個網路。我們微調時只改了類別數，所以可以直接沿用 Hailo 官方的 YOLOv8s 編譯設定。
- **複核用 CLIP，不用聊天模型**：複核只要回答「是」或「不是」，一個凍結的影像編碼器，加上主機端一個小小的矩陣乘法就夠了。在 PC 上每則警報只要 15 毫秒。
- **Qwen2.5-1.5B 走 Ollama 介面**：UGen300 上的 hailo-ollama 提供同一套介面，換到裝置上只要改一行設定（`llm.base_url`）。小模型就夠用，因為它起草的每條規則都會再經過程式檢查，日報的統計也全部由程式負責。
- **Whisper-Small**：Hailo GenAI Model Zoo 裡就有現成版本。

## Hailo 工具鏈上已經完成的事

雖然還沒拿到裝置，工地模式的兩個視覺模型都已經跑過 Hailo Dataflow Compiler 5.4.0，用的是 Hailo Model Zoo 的設定；我們也在 Hailo 的模擬器裡量了改成 INT8 之後準確率掉多少。這個模擬器的計算結果和晶片的整數運算逐位元相同。相關程式放在 `hailo/`。

- **安全帽偵測模型已編譯成 HEF**（Hailo-10H 執行的模型格式）：微調好的 YOLOv8s 先匯出成 ONNX，用 512 張校正圖片量化成 INT8，再編譯成 HEF。框的解碼和 NMS 都包在 HEF 裡，做法跟 Hailo 官方的 YOLOv8s 一樣；設定檔也已經指向這個檔案。
- **改成 INT8 幾乎沒有損失**：同樣 2,001 張測試圖片，Hailo 浮點版 mAP50 是 0.893，INT8 版是 0.889。浮點版和 PyTorch 原模型的結果一致，代表轉換本身沒有失真。
- **CLIP 編碼器已完成量化**：使用 Model Zoo 的 `clip_vit_b_32_image_encoder`。是非分類頭改用 INT8 特徵重新訓練後，準確率維持 95.3%，跟 PC 上一樣。
- **主機端程式已經寫好**：偵測模型的 HailoRT 後端（`sayguard/detectors/hailo_backend.py`）照 HailoRT 5.x 的 API 寫成，設定檔改成 `detector.backend: hailo` 就能切換。規則解析和日報本來就能接任何相容 Ollama 的伺服器。

| 模擬器驗證（Hailo-10H） | 轉換前 | INT8 |
|---|---|---|
| 安全帽偵測，2,001 張測試圖片的 mAP50 | 0.893（浮點） | **0.889** |
| 安全帽偵測的 mAP50-95 | 0.566（浮點） | 0.560 |
| CLIP 影像特徵與 PyTorch 的相似度（cosine） | 0.9999（浮點） | 0.9634 |
| 複核準確率（分類頭用 INT8 特徵重新訓練） | 95.3%（PC） | **95.3%** |
| 複核後仍保留的真實違規 | 94.9%（PC） | 93.9% |

表中兩個偵測數字都套用 HEF 內建的 NMS 設定，和 README 裡 0.939 的算法不同；0.889 只能拿來跟 0.893 比。

## 一台 UGen300 的負載

- **工地模式、10 支攝影機**：每支鏡頭每秒 10 張，合計每秒 100 張。在 PC 上，一個以批次處理的 YOLOv8s 實際每秒能分析約 105 張。以 Hailo 公布的 batch 8 每秒 252 張來算，大約只用到**一台 UGen300 的 40%**（估計值）。剩下的算力留給有物件規則的鏡頭跑 YOLO-World，以及警報複核；複核是每則警報跑一次，不是每張畫面都跑。儀表板上會即時顯示這個估計值（「UGen300 預估負載」）。
- **語言模型有需要才跑**：Whisper 和 Qwen2.5 只在有人講規則、或要產生日報時才會執行，不會一直佔用晶片。依參考速度推估，一句 5 秒的口述規則轉成文字約 2.4 秒、變成規則約 11.3 秒；一份完全由 LLM 撰寫的日報約 48 秒。PC 上一條規則只要 0.2–0.5 秒，裝置上確實比較慢，但工安人員一天只會加幾條規則，而且每條本來就要人工確認。

## Stage II 移植計畫（11/6 – 12/4）

1. **偵測模型上晶片（第 1 週）**：在主機裝好 HailoRT 和 UGen300 驅動程式，用 HailoRT 後端執行安全帽 HEF，實測 USB 連線下的處理量。倉庫偵測模型用同一套流程編譯（6 類、960 px 輸入、校正圖片只取自訓練場景），先在模擬器確認 INT8 準確率，再實測一台能不能撐住 12 支攝影機。
2. **警報複核上晶片**：把量化好的 CLIP 編碼器編譯成 HEF，再用晶片自己算出的特徵重新訓練是非分類頭，做法和模擬器裡驗證過的相同。
3. **語音和語言模型上晶片**：Whisper-Small 和 Qwen2.5-1.5B 改用 Hailo GenAI Model Zoo 的版本，Qwen2.5 由 hailo-ollama 提供服務，`llm.base_url` 改指向它。接著在裝置上重跑同一批口述規則和日報測試。
4. **到 ASUS 測試場地做整體實測**：一台主機配一台 UGen300 跑完整流程，量測每支鏡頭每秒處理的張數、警報延遲、裝置負載和功耗。

## 風險與對策

| 風險 | 對策 |
|---|---|
| **HailoRT 後端還沒在實機上跑過**。程式是照 HailoRT 5.x 的 API 寫的。 | 第 1 週第一件事就是驗證。HEF 的準確率已經在模擬器確認過，剩下要檢查的只是串接細節：輸出格式、影像縮放、批次處理。 |
| **USB 可能比 Hailo 公布的 PCIe 數據慢**。 | 工地模式只用到約 40% 的參考算力，還有餘裕。如果真的吃緊，就降低每支鏡頭每秒處理的張數，或把鏡頭分給兩台負責。 |
| **倉庫偵測模型比較吃算力，也還沒有 HEF**。960 px 輸入的每張運算量，比 640 px 的參考數據大；每台 12 支鏡頭的上限是依測試場景的涵蓋範圍訂的，不是算力實測的結果。 | 第 1 週就編譯並實測。如果一台撐不住 12 支 960 px 的鏡頭，就減少每台負責的鏡頭數，或改用較小的輸入尺寸。 |
| **Hailo 版 Qwen2.5-1.5B 的量化方式不同**，PC 上的準確率（工地 95%、倉庫 84–88%）不一定能直接沿用；規則解析也需要 hailo-ollama 支援 JSON schema 的 `format` 欄位。 | 不管 LLM 怎麼回答，檢查器都會核對數字、時間和物件。回覆如果不是合法的 JSON，規則解析和日報都會自動改走純程式的做法。我們也會在裝置上重跑同一批測試句子。 |
| **INT8 會讓 CLIP 特徵稍微偏移**（cosine 0.9634）。 | 用晶片算出的特徵重新訓練分類頭，模擬器裡的準確率是 95.3%。 |
| **視覺模型和語言模型共用一顆晶片**。Qwen2.5 起草規則或寫日報的那幾秒，偵測模型能用的時間會變少。 | 語言模型一次只跑幾秒，偵測又有餘裕。Stage II 會實測起草規則期間每支鏡頭的處理張數。 |

所有數據和量測方式見 [docs/results](results/README.zh-TW.md)；想自己重建 Hailo 檔案，請看 [SETUP.zh-TW.md](SETUP.zh-TW.md#重建-hailo-檔案)。
