# 倉庫模式（site mode）

工地模式（安全帽）把每支攝影機分開處理。倉庫模式（程式裡稱為 *site mode*）則把同一區域的所有攝影機當成
**同一個地方**：每支攝影機都經過校正，所以每個人的偵測框都會換算成平面圖上以公尺計的位置。同一位
作業人員被四支攝影機看到，只算一個人（而不是每支攝影機各算一次），每次進入只發一次警報（而不是每支
攝影機各發一次）；區域在平面圖上畫一次即可，不必每支攝影機各畫一次；「距離堆高機 3 公尺內」是在地面上
量出來的，而不是從頭部大小推估。

展示使用 NVIDIA PhysicalAI-SmartSpaces `Warehouse_010` 的 11 支同步、已校正攝影機（合成資料，
CC BY 4.0）。我們在倉庫偵測器從未訓練過的六座測試倉庫上，用 NVIDIA 的標準答案（ground truth）量測。
W010 同時也是展示場景，所以不是盲測（見[限制](#限制尚未量測的部分)）。以下內容都在 PC 原型（RTX 5060 Ti）
上執行；倉庫偵測器尚未編譯到 UGen300 上。

- 設定檔：[`configs/warehouse.yaml`](../configs/warehouse.yaml)
- 程式：[`sayguard/site.py`](../sayguard/site.py)（校正、平面圖、區域）、
  [`sayguard/sitetrack.py`](../sayguard/sitetrack.py)（每位作業人員一個身分、車輛）、
  [`sayguard/site_pipeline.py`](../sayguard/site_pipeline.py)（即時迴圈，以及與評估共用的融合程式）、
  [`sayguard/site_view.py`](../sayguard/site_view.py)（攝影機畫面與即時平面圖）、
  [`sayguard/rules/engine.py`](../sayguard/rules/engine.py) 中的 `RuleEngine.evaluate_site`（以人為單位評估規則）
- 評估：[`scripts/eval_site.py`](../scripts/eval_site.py)，各場景設定在 [`configs/eval/`](../configs/eval/)，
  結果在 [`docs/results/`](results/)（`site_eval*.json`；凍結版執行在 `docs/results/frozen/`）。本頁
  所有數字都抄自 [`docs/FACTS.md`](FACTS.md)。

## 執行

```bash
python scripts/fetch_smartspaces.py train/Warehouse_010     # calibration, floor plan, ground truth, 11 videos
python scripts/make_site_streams.py train/Warehouse_010     # frame-locked 1280 px, 10 fps streams (needs ffmpeg + ffprobe)
python -m sayguard serve --config configs/warehouse.yaml    # http://127.0.0.1:8000
```

另外需要倉庫偵測器權重 `@work/models/site_yolov8s.pt`（見[倉庫偵測器](#倉庫偵測器)）；若要用語音
規則，還需要與工地模式相同的 Ollama 相容伺服器（`qwen2.5:1.5b`）與 Whisper-Small。`@work` 是
repo 以外的工作目錄（`SAYGUARD_WORK`）。`start_demo_warehouse.cmd` 是作者在 Windows 上啟動同一指令
的批次檔，裡面的路徑是寫死的。

## 運作方式

每個時間點，所有攝影機的影格一起送進偵測器做一次批次推論；每支攝影機各自追蹤自己的人物框。接著：

### 1. 已校正的攝影機與平面圖

SmartSpaces 附有 `calibration.json`，每支攝影機都有：從地面（世界座標 z = 0，單位公尺）到影像像素的
3×3 單應矩陣（homography）、3×4 相機矩陣，以及平面圖轉換（平面圖像素 = (世界座標 + 平移) × 比例，
y 軸翻轉）。由 `Site.load` 讀入。串流的解析度比校正時低，所以每個點投影前都會先換算回校正解析度。

### 2. 從偵測框到地面位置：腳點、頭點與兩者之間的線段

- **腳點**：偵測框底邊中點，經反單應矩陣投影到地面。
- **頭點**：偵測框頂邊中點，用 3×4 相機矩陣投影到站立時頭頂高度（`HEAD_TOP_M`）的平面，再垂直落到
  地面。
- 被貨架、推車或畫面邊緣截斷的框，底邊不是腳，這時底邊會沿著相機視線投影到作業人員後方很遠的地方。
  因此每個視角都帶著從頭點到腳點的**地面線段**：人一定在這條線段上的某處。框若碰到畫面底邊，就視為
  看不到腳，改用頭點。長度超過 `MAX_SEGMENT_M` 的線段會捨棄（靠近地平線時投影會發散）。

### 3. 每個視角的不確定度

每個視角都有 `sigma`，也就是它在地面上的不確定度（公尺）：所用的點上一個像素在地面上跨越的距離，乘以
偵測框的定位誤差（幾個像素加上框高的一部分），並限制在 0.15–5 m 之間。在攝影機遠端、只有 40 px 高的人，
不確定度可達數公尺；靠近攝影機、看得清楚的人則落在這個範圍的下限。比對半徑會隨 `sigma` 放大，位置也依
它加權。

### 4. 融合：跨攝影機的同一位作業人員

`SiteTracker` 把各攝影機的追蹤軌跡變成地面上的作業人員。這裡沒有用外觀模型，身分完全靠幾何。

- **位置**：先取看得到腳的視角的加權中位數；再把每個視角移到它自己線段上最接近的點，重新取加權中位數。
  一個看不到腳的視角，無法把人拉到幾公尺外。
- **黏著連結**：攝影機軌跡會留在原本的作業人員身上，除非它持續與其他攝影機不一致（配錯，或兩個人一起
  走過來後分開）。
- **加入**：新的攝影機軌跡會加入其線段可及範圍內最近、且同一支攝影機沒有其他軌跡代表的作業人員。軌跡編號
  跳號，或人走進下一支攝影機的畫面，身分都不會變。
- **新增**：剩下的軌跡跨攝影機配對後成為新的作業人員。只有一支攝影機看到的軌跡必須先持續幾個時間點；位置
  不確定時要更久。閃爍的誤偵測不會變成一個人。
- **合併**：兩位持續靠近、且沒有共同攝影機的作業人員視為同一人；但若某支攝影機最近曾看到他們是分開站的
  兩個人，就要等更久才合併。保留較早的編號。
- **被遮住的人**：沒有攝影機看到的人，會在幾秒內保留編號；重新接上的半徑以步行速度放大，所以走到貨架後面
  不會變成新的人。編號永不重複使用。

儀表板上的人數就是作業人員數，旁邊的「cameras count N」是各攝影機自己人物軌跡的加總：同一個人被幾支
攝影機看到就算幾次。

### 5. 信心度過濾

偵測器以信心度 0.25 執行。某支攝影機以信心度 ≥ 0.7 看到某位作業人員時，才會**顯示**（上平面圖、算入人數、
交給規則評估）；之後只要仍有攝影機以 ≥ 0.6 看到就**保留**（`SHOW_CONF`、`KEEP_CONF`）。較弱的軌跡保留編號
但不顯示。車輛與機器人需要 ≥ 0.6（`OBJECT_CONF`）。這三個值都是在驗證場景（W020）上選的，從未在測試場景上
調整（`docs/results/w020_settings_analysis.json`）。在 W020 上，人員過濾把人員位置的精確率從 0.459（不過濾）
提高到 0.603，召回率則從 0.551 降到 0.521。信心度低於 0.6 的堆高機框中，6,284 個有 2,078 個是錯的，多半是
托板車與背景；≥ 0.6 的則是 11,103 個中 119 個。

### 6. 由著地點判斷車輛

規則不需要車輛的身分，只需要知道「現在這位作業人員附近有沒有車」。每個沒碰到畫面底邊的車輛框，取三個著地點
（兩個底角與底邊中點）投影到地面，再依類別跨攝影機分群。與作業人員的距離，是到任一攝影機看到的最近著地點的
距離，減去一段補償（車身可能伸出著地點之外）。堆高機的補償 0.1 m 是在 W020 上選的，把量測距離的偏差從
-0.38 m 降到 0.01 m。托板車、搬運車、移動機器人的補償只是粗估，沒有量測。機器人是偵測器的獨立類別，永遠
不會被算成作業人員。

### 7. 以地面區域定義規則

區域是平面圖上的多邊形（`plan_polygon` 用 `map.png` 像素，或 `polygon` 用公尺），寫在設定檔的 `zones:`
下，較具體的區域放前面。作業人員屬於所有包含其地面位置的區域，外加全場區域（`site.zone`，此處為
`warehouse`）。規則以人為單位評估，不以攝影機為單位（`RuleEngine.evaluate_site`）：

| 規則類型 | 在倉庫模式中 |
|---|---|
| `person_present` | 每位位於規則區域內的作業人員 |
| `person_count_over` | 規則區域內的作業人員，跨攝影機只算一次 |
| `object_near_person` | 每位作業人員到最近一台該類車輛的地面距離（公尺） |
| `object_present` | 規則區域內地面上有該類物件 |
| `no_helmet` | 拒絕：倉庫偵測器看的是整個人，不是安全帽 |

規則可以指名倉庫偵測器認得的任何類別（堆高機、托板車、搬運車、移動機器人、人形機器人）。規則提到的其他物件
則改用開放詞彙偵測器（YOLO-World），這在倉庫模式中尚未量測。每支攝影機看得到哪些地面區域，是依校正資料算一次，
只用來檢查草擬規則的範圍（「沒有攝影機涵蓋七號走道」）以及儀表板的涵蓋預覽；評估本身用的是作業人員的位置。

`configs/warehouse.yaml` 的兩條預設規則是「Keep 3 m from forklifts」（全倉庫，2 s）與「No walking in
aisle 7 (forklift parked)」（3 s），冷卻時間都是 60 s。

### 8. 警報邏輯：每人每次進入一次警報

- 條件必須持續達規則的 `min_duration_s`；短暫漏偵測不會讓計時歸零。
- 不論幾支攝影機看到，每位作業人員都是一個對象（`g<id>`），所以一條規則對一個人只發一次警報，而不是每支攝影機
  各發一次；之後由規則的 `cooldown_s` 控制提醒間隔。
- 幾十秒內，同一個人就可能換好幾個融合編號（W010 的 5 分鐘影片中每人 10.72 個編號）。因此當新編號出現在已發過警報的人所在位置時，引擎要判斷是不是
  同一人。如果那位作業人員原本的編號**仍在追蹤中**，新編號只有在正好站在他身上時才算同一人（同一人身上出現第二個
  編號）。如果原本的編號**已經消失**，新編號在 10 s 內（`SITE_REAPPEAR_S`）出現在他被警報的位置附近，或在
  3 s 內（`SITE_HANDOVER_S`，半徑以步行速度放大）出現在他最後被看到的位置附近，才算同一人。其他人，例如同一條
  走道上的下一位作業人員，會收到自己的警報。
- 同一位置的新編號也會沿用被取代編號已累積的持續時間，所以編號跳動不會讓計時重來。
- **重新進入**：作業人員離開區域至少 10 s（`SITE_REENTRY_S`）後再回來，存在型規則會再發一次警報，不受冷卻時間
  限制。冷卻時間的用意是在有人一直停留時拉開提醒間隔，不應延續到這個編號下一個代表的人。
- 全場型規則（人數、物件出現）以整個場地為單一對象，警報會掛在最能看到觸發原因的那支攝影機上。

### 9. 儀表板顯示內容與隱私

- 即時平面圖（`/stream/map`）顯示區域、攝影機位置、以圓點表示的作業人員（警報中為紅色）、車輛，以及接近警報
  進行中時標示距離（公尺）的紅線。攝影機畫面中，警報中的作業人員在每支看得到他的攝影機上都以紅框標示。
- **不顯示作業人員編號。** 編號在任一時刻都可靠，但幾十秒內就會更換（W010 的 5 分鐘影片中每人 10.72 個編號，
  IDF1 0.516），畫面上顯示編號會誤導。警報紀錄會保留內部編號、攝影機與地面位置供日誌使用。
- 所有攝影機畫面與快照中，每個偵測到的人物框的**臉部都會打馬賽克**。倉庫偵測器沒有頭部框，所以臉部區域是從
  每個人物框的上緣推估。偵測器回傳的每個人物框都會打碼，包括追蹤器沒採用的框。這個推估漏掉臉的頻率（例如作業
  人員彎腰時）沒有量測。
- 一切都在現場本地執行（目前是 PC 原型；第二階段改在 UGen300 上），影格與警報不會送到任何雲端服務。

## 倉庫偵測器

現成偵測器在合成倉庫上不堪用：在 Warehouse_010 上，YOLO-World 在 30 個堆高機框中找到 0 個；COCO YOLOv8s 只把
7 個當成「truck」，還把 39 % 的人形機器人當成人。所以 SayGuard 自己訓練偵測器：**YOLOv8s、6 類**（person、
forklift、pallet truck、transporter、mobile robot、humanoid robot），以 960 px 在 5 棟合成建築、8 個 SmartSpaces
訓練場景（W000、002、004、006、008、011、014，以及 W016 的攝影機 0-8；W000、002、004、006 是同一棟建築）的
8,000 張影像上微調，從未用任何評估場景訓練。
`scripts/prepare_site_dataset.py` 會直接拒絕 W010、W018、W020；其他評估場景只是不在訓練清單裡。即時執行時，
在 RTX 5060 Ti 上一個 960 px 的 11 張影格批次約需 63-95 ms。權重：`@work/models/site_yolov8s.pt`。Hailo HEF
（`site_yolov8s.hef`）尚未建置。

## 倉庫的語音規則

規則可以用國語或英語說出來，和工地模式一樣，原則也相同：**LLM 提案、程式檢查、安全主管確認**。
Qwen2.5-1.5B 依 JSON schema 起草規則；確定性的規則擷取器會覆寫它在句子中找到的類型、物件、數字、距離或時間（它可能
漏掉某些說法）；只說了區域沒說攝影機時，規則涵蓋所有攝影機，因為區域是地面上的一塊範圍，不是某支攝影機。安全主管
確認草稿後規則才生效。針對倉庫做的修正：含數字或數字詞的區域名稱、可省略的「區」、距離的說法、停留類動詞、
「N 人以上」，以及緊鄰中文的「AMR」。

測試句（`tests/site_rule_sentences.json`）由從未看過解析器程式碼的 AI agent（撰寫者與審核者）撰寫並標註。這些是
打字輸入的句子：語音辨識不在這些數字裡，其準確度也沒有量測。每個標註欄位都對，才算答對。所有執行都在 PC GPU 上
使用 Ollama `qwen2.5:1.5b`；UGen300 上的 Hailo GenAI 版本沒有量測。

| 句組 | 句數 | 只用 LLM | 只用規則擷取器 | LLM + 檢查 | 延遲（平均 / 最大） |
|---|---|---|---|---|---|
| dev（可用來修解析器） | 15 | 0.2 | 1.0 | **1.0** | 363 / 457 ms |
| held-out v1 首次執行（修正它暴露的問題之前） | 25 | 0.16 | 0.8 | **0.84** | – |
| held-out v1 修正之後（之後已看過，不再乾淨） | 25 | 0.16 | 0.96 | 1.0 | 392 / 515 ms |
| held-out v2（全新、盲寫、從未用於調整） | 25 | 0.24 | 0.68 | **0.88** | 395 / 638 ms |

誠實的數字是全新的那組：88 % 完全正確，只用 LLM 則是 24 %。離線（不用 LLM）時，只用規則擷取器在全新那組答對 68 %。

## 評估方法

### 場景與角色

有些 SmartSpaces 場景是**同一組攝影機的雙胞胎**（000/001、002/003、004/005、006/007、008/009、017/018、020/021）：
同一棟建築、同一組攝影機，`calibration.json` 與 `map.png` 逐位元相同。建築是依平面圖（`map.png`）區分的：W000–W007
與 W020/021 是同一棟建築（五組攝影機），其餘每對雙胞胎或單一場景各有自己的平面圖。沒有任何測試場景與訓練場景共用
平面圖；W018 只與開發場景 W017 共用。各場景的角色如下：

| 角色 | 場景 | 用途 |
|---|---|---|

### 量測內容

`scripts/eval_site.py` 逐格執行即時融合（`SiteFusion` 與 `RuleEngine.evaluate_site`，與儀表板相同的程式），跑完整段
同步影片（3000 格、10 fps；W022 為 3090 格），再與 NVIDIA 的標準答案比對；標準答案知道每個人的地面位置，且同一人
在每支攝影機中編號相同。標準答案從不進入處理流程。

- **人數**：每格顯示的作業人員數，對比至少有一支已設定攝影機看得到的真實人數，以及各攝影機加總。以平均值與平均
  絕對誤差呈現。
- **位置與身分**（`motmetrics`，比對半徑 1 m）：召回率、精確率、MOTA、平均位置誤差（公尺）、IDF1。*重複* 是同一時間
  一個人身上有兩個編號的人次比例（多對一比對；一對一的 MOT 比對會把它藏起來）。*每人編號數* 是每個真實的人在整段
  影片中被拆成幾個場地編號。
- **事件**：標準答案事件是指一個人在堆高機 3D 佔地範圍 3 m 內持續規則的 2 s，或在某區域內持續規則的時間；短於 1 s
  的中斷不會拆開事件。加上 `--all-zones` 時，每個沒有存在型規則的區域也會加一條（「Zone check: <zone>」，3 s，冷卻
  60 s）。
- **警報**：警報當下，若其作業人員距離某事件的人 2.5 m 內，該警報就歸給同規則的那個事件；對不到任何事件的警報就是
  **誤報**。**嚴格召回率** 只算有自己警報的事件；**涵蓋** 另外也算事件開始前、冷卻時間內已因同一規則對該人發過警報的
  事件——依設計，這些事件不會再發新警報。*每個被警報事件的警報數* 是對到事件的警報數除以有警報的事件數（1.0 表示
  每個事件剛好一次）。
- **逐攝影機基準**：相同的偵測結果與相同的地面距離，但每支攝影機只對自己的軌跡發警報，並套用 SayGuard 以前的去重
  機制（同位置 IoU、每支攝影機 15 s 間隔、每支攝影機一個存在型對象）。
- **堆高機**：*找到* 是堆高機影格（某支已設定攝影機看得到堆高機）中，偵測到的堆高機著地點落在其佔地範圍 2.5 m 內的
  比例。*距離誤差* 是量到的人員到堆高機距離減去標準答案中到 3D 佔地範圍的距離，只計算距離某台堆高機 6 m 內、且該堆高機
  有被偵測到的人。
- JSON 檔中還有 `alerts_in_view`（只算在某支攝影機中至少 40 px 高的人）。下表使用 `alerts`，也就是所有事件。

### 區域

`configs/eval/*.yaml` 中的區域，是在涵蓋圖上（至少兩支攝影機能看到站立者高度 ≥ 40 px 的範圍）由未看過任何結果的
審核者（另外的 AI agent）畫出。畫該場景區域的 agent 也只根據涵蓋圖，給每個區域一個種類：門口 / 碼頭、走道（狹窄
通道與走道）、作業區或其他。種類記錄在 `docs/results/site_by_zone_kind.json`，不在 eval 設定檔中。W010 沿用展示用的
`configs/warehouse.yaml` 區域，所以它的區域不是盲畫的；種類由我們指定：aisle 7 走道、dock 門口、racks 與 open floor
作業區。

agent 給的種類並不完全一致：W015 的 `west_rack_aisle` 是作業區，`east_rack_aisle` 卻是「其他」；W022 的
`picking_aisle_r2_r3` 是作業區，`main_aisle_r1_r2` 卻是走道。我們保留 agent 原本的標註。種類檔是在有結果之後才寫的，
eval 設定檔也沒有記錄種類，所以 repository 裡沒有結果出來之前的種類紀錄。「其他」這一列
只有 `east_rack_aisle`（W013 的 `west_rack_line` 沒有事件），下面每張表都有列出，而且它是誤報率最高的種類。

### 先凍結版執行，再最終執行

首先是**凍結版執行**：在每個場景上用出貨的偵測器與信心度設定，結果原樣保留（`docs/results/frozen/`）。看過凍結版
結果之後，才在開發與驗證場景（W009、W012、W017、W020）上發展了兩項警報邏輯修改，從未用測試場景：

1. 同一人判定改為考慮對方是否仍在場：新編號只有在原作業人員的編號已消失時（重新出現 10 s / 交接 3 s），或正好站在他
   身上時，才算是已警報的那個人。
2. 存在型規則在離開 10 s 後重新進入時再發警報。

之後測試場景只重跑一次（`docs/results/`）。兩次執行的偵測器與信心度設定相同。下面的主要數字來自這次最終執行，
凍結版並列在旁。

### 在驗證場景（W020）上選定的設定

- 某支攝影機以信心度 ≥ 0.7 看到時顯示作業人員，≥ 0.6 時保留；車輛需要 ≥ 0.6。
- 堆高機距離補償 0.1 m（W020 上的偏差從 -0.38 m 變為 0.01 m）。
- 「看得到」= 在 1280×720 下高度 ≥ 40 px。在 W020 上，20-40 px 高的人偵測率 68 %，40-80 px 則為 92 %。

## 限制：尚未量測的部分

- **只有合成影片。** 所有數字都來自算圖產生的 SmartSpaces 倉庫。真實影片（蹲下、搬運物品、反光、實際攝影機擺放）
  尚未量測。
- **必須校正。** 攝影機需要地面單應矩陣與 3×4 相機矩陣。SayGuard 還沒有校正工具，真實場地會需要一個。
- **長時間的身分。** 融合後的編號在幾十秒內就會更換（W010：5 分鐘影片中每人 10.72 個編號，IDF1 0.516）。目前
  沒有外觀重新辨識；Hailo 的人員重新辨識網路是規劃中，尚未建置。
- **W010 並非完全獨立。** 偵測器從未用它訓練，但它是展示場景，追蹤器是看著它開發的（`sitetrack.py` 引用了它的標準
  答案），而且它的區域沿用展示設定，不是盲畫的。它的數字不如其他五個測試場景獨立。
- **W018 與警報邏輯。** 用來發展警報邏輯的 W017，與測試場景 W018 是同一棟建築、同一組攝影機。兩項警報邏輯修改
  是在看過凍結版結果之後做的（在 W009、W012、W017、W020 上）。
- **樣本小。** 有幾個區域完全沒有事件。W018 平均只看得到 1.0 人；W022 的 north staging 只有 4 個事件。單一
  區域的百分比請謹慎看待；依區域種類的彙總比較穩定。
- **W018 與 W019 的堆高機偵測偏弱**（只在 0.169 與 0.115 的堆高機影格中找到，W022 為 0.793，W010 為 0.986）。原因
  尚未確定。規則在 W018 與 W019 仍涵蓋了 8 個中的 8 個與 11 個中的 8 個事件。用客戶自己的車輛微調是規劃中的改善方式，
  效果多大沒有量測。
- **嚴格召回率低於涵蓋率。** 堆高機規則 60 s 的冷卻時間刻意不對在停放堆高機 3 m 範圍進進出出的同一位作業人員重複
  警報，所以測試場景的嚴格召回率是 41 %，涵蓋率則是 92 %。W010 的堆高機規則涵蓋 0.952 的事件，但直接警報的只有
  0.429。
- **超出規格時最差。** W020（16 支攝影機）MOTA 0.168，堆高機事件只涵蓋 0.568，51 次警報中有 16 次誤報。W020 的人數
  也最多，而且是訓練用的那棟建築，所以並未證明攝影機數量就是原因。
- **完全沒有量測：** 此模式下的開放詞彙備援、堆高機以外車輛的補償、推估的臉部區域漏掉臉的頻率、區域之間的交接
  （未實作：走到另一區的人會得到新編號）、口述倉庫規則的語音辨識（解析測試句是打字輸入的）、LLM 在 UGen300 上的
  表現（Hailo GenAI 版本），以及倉庫偵測器在 Hailo-10H 上的表現（HEF 尚未建置）。凍結版執行無法從目前的程式重跑：
  較早的警報邏輯沒有保留，`docs/results/frozen/` 就是紀錄。

## 部署規格

- **每個不超過 12 支攝影機的區域配一台 UGen300。** 較大的建築切成數個區域，各有自己的平面圖與設定檔。
- **受監看的區域必須有 ≥ 2 支攝影機以 ≥ 40 px 看到**（站立者高度至少 40 px）。

12 支攝影機的上限是涵蓋規格：測試場景（3 到 11 支攝影機）都在範圍內，超出範圍的 W020（16 支攝影機）追蹤結果是所有
場景中最差的，但並未證明攝影機數量就是原因（見上文）。40 px 的規則來自驗證場景：在 W020 上，人員偵測率從 40-80 px
的 92 % 降到 20-40 px 的 68 %。兩者都不是運算量的數字。一台 UGen300 能否用這個 960 px 偵測器撐住 12 支攝影機，因為
HEF 尚未建置，目前還沒有量測；這項量測排在第二階段第 1 週。

### 依區域種類彙總

repo 中沒有計算它的腳本。在 repo 根目錄執行以下 Python，即可重現測試場景的彙總表（把 `docs/results/` 改成
`docs/results/frozen/` 就是凍結版）：

```python
import json, collections
KIND = {"Keep 3 m from forklifts": "forklift", "No walking in aisle 7 (forklift parked)": "lane",
        "dock": "door", "loading_dock_staging": "door", "dock_staging_area": "door",
        "west_cross_aisle": "lane", "north_cross_aisle": "lane", "staging_west_walkway": "lane",
        "dock_side_aisle": "lane", "main_aisle_r1_r2": "lane",
        "west_rack_line": "other", "east_rack_aisle": "other"}          # every other zone: work
tot = collections.defaultdict(lambda: [0, 0, 0, 0, 0])                 # events, own alert, covered, alerts, false
for f in ["site_eval"] + [f"site_eval_warehouse_{n}" for n in ("013", "015", "018", "019", "022")]:
    for rule, s in json.load(open(f"docs/results/{f}.json"))["alerts"]["site"].items():
        t = tot[KIND.get(rule.removeprefix("Zone check: "), "work")]
        for i, v in enumerate((s["events"], s["events_alerted"], s["events_alerted"] + s["events_in_cooldown"],
                               s["alerts"], s["false_alerts"])):
            t[i] += v
for k, (e, o, c, a, fa) in tot.items():
    print(f"{k:8s} covered {c}/{e}  strict {o}/{e}  false {fa} of {a}")
```

### 倉庫偵測器

出貨的權重來自兩次訓練：先在四個場景上訓練出第一版模型，再接著在八個場景的資料集上續訓。GPU 訓練不是逐位元可重現，
重建出來的權重會相近，但不會完全相同。

```bash
# fetch each scene first: python scripts/fetch_smartspaces.py train/Warehouse_000 (and 002, 004, 006, 008, 011, 014, 016)
python scripts/prepare_site_dataset.py --train train/Warehouse_000 train/Warehouse_004 train/Warehouse_008 train/Warehouse_014 --val train/Warehouse_016 --name site
python scripts/train_detector.py --data @work/datasets/site/data.yaml --name site_v8s --out site_v1_best.pt --imgsz 960 --epochs 30 --batch 16
python scripts/prepare_site_dataset.py --train train/Warehouse_000 train/Warehouse_002 train/Warehouse_004 train/Warehouse_006 train/Warehouse_008 train/Warehouse_011 train/Warehouse_014 "train/Warehouse_016:~9,10" --val "train/Warehouse_016:9,10" --name site_v3
python scripts/train_detector.py --model site_v1_best.pt --data @work/datasets/site_v3/data.yaml --name site_v8s_v3 --out site_yolov8s.pt --imgsz 960 --epochs 20 --batch 16
```
